# Evidence policy

> 证据(verification evidence)的可校验定义。所有 skill 出口引用本文件判断「声明完成」是否合法。

## 为什么单独定义

「运行证据」如果只是文字,会退化成自报结论——模型写「测试通过 45 条」和真的跑过命令是两件事。本文件把「证据」钉死成可校验的形态:**不是结论,是执行回执**。

## 什么是证据(合法)

一个证据项 = 一个**实际执行过的命令** + 它的**真实输出**,二者缺一不可:

| 形态 | 示例 |
|------|------|
| 命令 + 退出码 | `npm test` → exit 0 |
| 命令 + 关键输出行 | `tsc --noEmit` → `Found 0 errors.` |
| 命令 + 报告路径 | `pytest` → `2 passed, 0 failed`（输出片段或 CI 报告链接） |
| bugfix 红灯回执 | 修复前 `npm test` → exit 1（失败行）+ 修复后 `npm test` → exit 0（两次都要） |

## 什么不是证据(非法,即便措辞像)

| 说法 | 为什么不算 |
|------|-----------|
| 「测试通过」「编译成功」 | 这是**结论**。证据是命令 + 输出,不是结论。 |
| 「我检查了一下代码」「看起来对」 | 这是**检查(inspect)**,不是**验证(verify)**。验证必须有执行。 |
| 「逻辑上应该没问题」 | 这是**推理**,不是证据。 |
| 只断言常量矛盾、不调用被测代码的测试 | 无法证明修复有效,不是 red-capable。见 bugfix-protocol。 |

> 区分 inspect 与 verify:读代码、走查逻辑、对照文档 = inspect;跑命令、看真实输出 = verify。**inspect 不满足 D9**。

## 强度分级(随 D10 风险递增)

证据重量随任务复杂度递增,不是一刀切:

| D10 级别 | 证据要求 |
|---------|---------|
| L0 / L1 | ≥1 命令回执,对话可见即可 |
| L2 / L3 | 命令回执**写入 Change Unit 的 Evidence 段** + 关键路径(触及 P0/P1 风险)走独立 subagent 复核 |

降级不缩小验证地板:L0 也必须有 ≥1 命令回执,只是不需要落盘和 subagent。

## 合法出口:无法执行时

无法提供命令回执时,**标记 `⚠️ 未验证` + 说明阻塞原因**是合法出口,不强制无中生有:

- 纯文档项目、无运行时、环境不可用 → `⚠️ 未验证: <具体阻塞原因,如"无 Node 运行时"或"需数据库才能验证">`
- 这种标记必须显式,不能静默跳过验证又声明完成

## 存储

证据收敛进 **Change Unit 的 Verification / Completion Evidence 段**,不生成独立 trace 文件。对话里给摘要,持久化进 CU。

## 边界(已知限制)

本文件定义的是**skill 文档层**的约束。它要求模型交出命令回执,但**无法在 harness 层面校验命令输出是否被伪造**——模型可以编造一个看起来真实的 `npm test` 输出。彻底堵这个洞需要运行时执行回执(超出 skill 文档能力范围)。review 的独立 subagent 复核是当前 suite 内对「伪造输出」的唯一压力。
