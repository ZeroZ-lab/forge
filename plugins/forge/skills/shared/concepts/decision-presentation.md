# Decision Presentation — 决策呈现规则

> 协议规则：决策语义不绑定宿主工具；交互载体按“宿主适配与降级”规则选择，不得改变 Recommended、tradeoff 或 custom 语义。

## 核心原则

**先研究，再呈现。** AI 先搜索、分析或推导，再把收敛后的 2–4 个有效选项交给用户选择。

**选择优于填空。** 能可靠枚举选项时，不要求用户从零发明答案；无法可靠枚举时才用开放式自然语言收集上下文。

## 语义契约

所有宿主实现都表达同一组字段：

```yaml
question: 状态管理选什么方案？
header: 状态管理
options:
  - label: Zustand
    impact: 轻量且接入成本低，但约束和配套工具较少
  - label: Redux Toolkit
    impact: 约束和工具成熟，但样板与学习成本更高
  - label: Jotai
    impact: 适合细粒度状态，但团队需要适应原子模型
recommended: Zustand
allow_custom: true
```

- `question`：当前必须决定的问题。
- `header`：便于扫描的短标签。
- `options`：2–4 个互斥选项；每项包含 label 和一句 impact/tradeoff。
- `recommended`：基于现有证据的默认建议；展示时标为 `(Recommended)`。
- `allow_custom`：始终允许用户给出未列出的方案。

## 宿主适配与降级

- structured choice 能完整表达当前候选数和全部语义字段：把语义契约映射到宿主的结构化控件，不依赖特定工具名或参数名。
- 没有该能力，或控件的选项数、推荐、tradeoff、custom 任一约束无法表达：用 numbered options 呈现同样的信息，例如：

  1. Zustand — Recommended：接入成本低，但约束较少。
  2. Redux Toolkit：工具成熟，但样板较多。
  3. Jotai：粒度灵活，但需要适应原子模型。
  4. Custom：提供你的方案。

- 降级只改变交互载体，不改变问题、选项、推荐、取舍或自定义能力。

## 什么时候呈现选择

选项可枚举，且用户需要在 2–4 个明确方案之间作决定时使用上述选择协议。

| 场景 | 例子 |
|------|------|
| 技术选型 | 框架选 Next.js 还是 Hono？ |
| 策略选择 | 分页选 page 还是 cursor？ |
| 范围决策 | 多租户这个版本做不做？ |
| 方向选择 | brainstorm 收敛时推荐方向 A 还是 B？ |
| 参数确认 | 帧率目标 30fps 还是 60fps？ |
| 流程分支 | 先做 API 详设还是先做前端详设？ |

## 什么时候用开放式自然语言

选项无法可靠枚举，需要用户描述场景、补充事实或展开思维时，直接提问，不伪造候选项。

| 场景 | 例子 |
|------|------|
| 开放式探索 | 你的用户是谁？他们最痛的点是什么？ |
| 场景描述 | 描述一个真实的使用场景。 |
| 发散思维 | 有没有想过完全不同的方向？ |
| 上下文收集 | 这个功能的数据量大概多大？ |
| 发散阶段 | brainstorm 的理解和展开阶段。 |

## Skill 决策点中的判断

每个 skill 的决策点（`### XX: 主题`）都有 `**问**` 和 `**记录**`。判断方法：

| 决策点特征 | 呈现方式 |
|-----------|---------|
| `**问**` 是在几个方案间选择 | 按“宿主适配与降级”规则呈现 |
| `**问**` 是开放描述 | 自然语言 |
| `**不变原则**` 有明确的 A > B 排序 | A 标 Recommended，并说明证据与 tradeoff |
| 需要先搜索或推导才有选项 | 先研究，再呈现选择 |

混合模式允许先用自然语言收集上下文，再按语义契约呈现选项；不得在证据不足时提前收敛。

## 执行顺序

1. **读决策点**：理解 `**问**`、约束和 `**不变原则**`。
2. **研究/推导**：根据上下文搜索方案并分析利弊。
3. **收敛选项**：筛选 2–4 个值得选择的方案，或确认问题仍需开放描述。
4. **呈现选择**：按“宿主适配与降级”规则映射交互载体。
5. **记录决策**：把用户选择、理由和被拒方案写回对应权威产物。
