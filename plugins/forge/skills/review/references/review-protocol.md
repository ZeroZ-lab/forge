# Review Protocol

## 文档审查维度

### 1. 文档完整性

- 是否有 WHAT：需求、验收条件、边界。
- 是否有 WHY：选择理由、拒绝方案、决策编号（PD# / FD# 前缀与来源文件匹配）。
- 是否有 HOW：数据模型、接口、状态码、目录映射。
- 是否有 CONSTRAINTS：安全、性能、兼容、权限、租户。
- 是否残留未解决的 `[NEEDS CLARIFICATION: ...]`：有则阻塞；任何依赖该事实的实现开始前必须解决或升级人类决策。

### 2. 跨文档一致

- project.md 技术选型是否和 goal.md 一致。
- DESIGN.md 是否被 frontend modules 消费。
- API modules 是否和 database specification 对齐。
- plan 是否覆盖所有 modules 和验收条件。
- testing 是否从 goal 和 modules 推导，而不是另起一套。

### 3. 可消费性

- 路径是否无歧义。
- 入口文件是否明确。
- 公共接口和内部函数是否区分。
- 参数类型签名是否完整。
- 模块依赖关系是否可重建。

### 4. 偏差归因复审

- codegen 验证摘要的归因（skill 方法论 / 文档未同步 / 代码实现）是否准确。
- 中止项的中止理由是否合理（确属目标矛盾或需求歧义，不是借口）。
- 是否有真实偏差被"自动修正"轻轻带过、未上报。

## 代码审查维度

### 1. 目标一致

- 路由、schema、service、db、tests 是否满足声明的目标。
- 错误码、响应结构、权限、幂等是否一致。
- 共享约束是否贯穿所有相关文件。

### 2. 决策遵循

- 关键逻辑是否引用决策编号（FD# / PD#）。
- 代码是否偷偷做了未记录的新决策。
- 持久变更是否有 Change Unit，且权威文档已同步。

### 3. 测试真实性

- 测试是否覆盖正常、边界、错误。
- 是否存在 placeholder 测试。
- 是否只验证实现细节而没验证规格行为。
- bugfix 的红灯测试是否真实锚定被测代码路径（调用真实代码 / 真实数据），还是只断言常量矛盾（见 `${CLAUDE_SKILL_DIR}/../shared/concepts/evidence-policy.md`）。只断言常量的红灯无法证明修复有效，视为假红灯。
- codegen 交出的「验证证据」是否含命令回执（命令 + 真实输出），还是只有「测试通过」「编译成功」这类结论字符串。结论不是证据。

## 偏差归因维度

每个问题归因到三层根因之一：

| 归因层 | 含义 | 后续流向 |
|--------|------|---------|
| **skill 方法论** | skill 的决策点或方法论有盲区，导致遗漏 | 写入报告，供 learn 消费 |
| **文档未同步** | 文档间不一致（上游改了下游没跟） | 级联更新（中回路） |
| **代码实现** | 代码未满足目标要求 | 修代码 |

**归因判断**：
- 文档里**没提**这个问题 → 大概率 skill 方法论（文档没写 = 方法论没引导）
- 文档里**写了**但下游没同步 → 文档未同步
- 文档里**写了**且下游同步了但代码没实现 → 代码实现

```markdown
- Residual risk:

## 归因汇总

| 归因类型 | 数量 | 具体条目 | 后续流向 |
|---------|------|---------|---------|
| skill 方法论 | | | learn（/forge:learn 归档） |
| 文档未同步 | | | 级联更新 |
| 代码实现 | | | 修代码 |
```

## Subagent Prompt 要点

让独立审查者明确：

- 你的任务是找失败模式，不是改代码。
- 优先报告 P0/P1。
- 每个问题必须有文件、证据、影响和修复建议。
- 不要把缺少运行证据说成通过——「测试通过」「编译成功」是结论，不是证据；证据是命令 + 真实输出。把只有结论、无命令回执的验证项标记为「证据缺失」。
- 如果文档和代码冲突，以文档作为源头，除非文档本身缺失或矛盾。
- 对每个问题做偏差归因：skill 方法论 / 文档未同步 / 代码实现。

## 复审规则

阻塞项修复后必须重新审查同一范围。复审报告只需覆盖：

- 原问题是否关闭。
- 是否引入新问题。
- 是否仍有残余风险。
