# Interaction Design — 设计阶段（交互层）

## 职责

定义用户如何与产品交互，包括用户流程、信息架构、组件复用。

**原则**：先画用户怎么走，再画界面长什么样。流程比视觉更重要。

## 决策点

### I1: 用户流程

**问**：
- 用户从进入产品到完成核心任务，需要经过哪些步骤？
- 每个步骤用户需要什么信息？能做什么操作？
- 异常流程怎么处理？（错误、取消、超时）

**不变原则**：
- 核心操作 3 步内完成
- 每个操作必须有反馈（成功/失败/进行中）
- 错误处理 > 错误预防（用户犯错时要有明确的提示和恢复路径）

**记录**：用户流程图 + 每步的信息需求 + 操作列表 + 异常处理

### I2: 信息架构

**问**：
- 产品有哪些核心概念？（任务、项目、用户、团队）
- 这些概念之间的关系是什么？（一对多、多对多）
- 用户如何在这些概念之间导航？

**不变原则**：
- 信息架构要反映用户的心智模型（不是技术模型）
- 导航层级不超过 3 层
- 核心概念要有独立的入口（不要藏在深层菜单里）

**记录**：信息架构图 + 概念关系 + 导航结构

### I3: 页面布局

**问**：
- 每个页面需要展示哪些信息？
- 信息的主次关系是什么？（主要信息 vs 辅助信息）
- 页面之间的跳转关系是什么？

**不变原则**：
- 每个页面只有一个主要目标
- 主要信息占据视觉中心
- 页面跳转要有明确的路径（不要让用户迷路）

**记录**：页面线框图 + 信息层级 + 跳转关系

### I4: 组件复用

**问**：
- 哪些交互模式会重复出现？（列表、表单、弹窗、卡片）
- 这些组件需要支持哪些变体？（大小、状态、主题）
- 组件之间的组合规则是什么？

**不变原则**：
- 组件复用 > 定制开发
- 组件要有明确的职责边界（一个组件只做一件事）
- 组件组合要有规则（不是任意组合）

**记录**：组件清单 + 变体定义 + 组合规则

### I5: 交互细节

**问**：
- 操作反馈的形式是什么？（Toast、Modal、Inline）
- 加载状态怎么展示？（骨架屏、Spinner、进度条）
- 空状态怎么展示？（引导、占位图、CTA）

**不变原则**：
- 反馈要及时（操作后 100ms 内）
- 加载状态要减少焦虑（告诉用户"正在做什么"）
- 空状态是机会（引导用户下一步行动）

**记录**：反馈规则 + 加载状态 + 空状态设计

## 文档约束

**interaction-spec.md 必须包含：**
1. 用户流程图（核心流程 + 异常流程）
2. 信息架构图（核心概念 + 关系 + 导航）
3. 页面线框图（每个页面的布局 + 信息层级）
4. 组件清单（复用的组件 + 变体 + 组合规则）
5. 交互细节（反馈、加载、空状态）
6. 响应式策略（移动端 vs 桌面端）

**interaction-spec.md 不应包含：**
- 视觉设计（那是 visual-design 的事）
- 具体技术实现（那是 /forge-detail 的事）
- 代码实现（那是 生成代码 的事）

## 恒久约定

### 用户流程格式
```markdown
## 用户流程

### 核心流程：创建任务
1. 用户进入任务列表页
2. 点击"新建任务"按钮
3. 填写任务表单（标题、描述、负责人、截止日期）
4. 点击"保存"
5. 任务出现在列表中

### 异常流程
- 表单验证失败 → 显示错误提示，保留用户输入
- 网络错误 → 显示 Toast，提供重试按钮
- 权限不足 → 显示权限申请引导
```

### 信息架构格式
```markdown
## 信息架构

### 核心概念
- 项目（Project）：任务的容器
- 任务（Task）：具体的工作项
- 用户（User）：系统使用者
- 团队（Team）：用户的分组

### 概念关系
- 项目 1:N 任务
- 项目 N:M 用户（通过团队）
- 任务 N:1 用户（负责人）

### 导航结构
- 首页 → 项目列表
- 项目详情 → 任务列表
- 任务详情 → 评论、附件
```

### 组件清单格式
```markdown
## 组件清单

### TaskCard（任务卡片）
**用途**：在列表中展示任务概要  
**变体**：
- 状态：pending / in-progress / completed
- 优先级：low / medium / high
- 尺寸：small / medium / large

**组合规则**：
- 可以嵌套在 TaskList 中
- 可以点击打开 TaskDetail
- 可以拖拽排序
```

## 入口/出口条件

**入口条件**：
- 有 PRD.md（来自 /forge-requirements）
- 或用户已有明确需求（跳过 define）

**出口条件**：
- 生成了 interaction-spec.md
- 用户流程已定义（核心流程 + 异常流程）
- 信息架构已明确（核心概念 + 关系 + 导航）
- 组件清单已确定（复用的组件 + 变体）
- 用户确认是否继续（进入 visual-design 或 /forge-detail）

## 何时不使用

- 纯后端 API（没有用户界面）
- 已有完整的交互设计（直接进入 visual-design）
- 小功能迭代（简化交互流程）

## 红旗清单

- 核心操作超过 3 步 → 强制简化（"能不能合并某些步骤？"）
- 没有异常流程 → 强制补充（"出错了怎么办？"）
- 组件复用率低 → 强制抽象（"哪些交互模式重复出现？"）
- 信息架构超过 3 层 → 强制扁平化（"能不能减少层级？"）
- 没有空状态设计 → 强制补充（"第一次使用时展示什么？"）

## 验证清单

- [ ] 核心流程是否在 3 步内完成？
- [ ] 是否有异常流程（错误、取消、超时）？
- [ ] 信息架构是否反映用户心智模型？
- [ ] 导航层级是否不超过 3 层？
- [ ] 组件复用是否充分（避免重复造轮子）？
- [ ] 是否有反馈、加载、空状态设计？
- [ ] 响应式策略是否明确（移动端 vs 桌面端）？
