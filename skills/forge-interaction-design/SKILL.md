# Interaction Design — 设计阶段（交互层）

## 职责

设计用户怎么和产品交互——路径优先，先画用户怎么走，再画界面长什么样。

**核心洞察**：好的交互设计是看不见的——用户不需要"学"就会用。流程比视觉更重要，模式比定制更高效。

**方法论**：流程→结构→模式→细节。

## 与上下游的边界

**上游**：读 PRD（forge-define 产出），不重复需求定义
**下游**：交互规格交给 fe-system（定义外观）和 /detail（技术实现）

**和 fe-system 的切法**：
- interaction 定义**组件做什么**（行为、组合规则、交互模式）
- fe-system 定义**组件长什么样**（外观、色彩、间距、状态样式）

## 方法论：流程→结构→模式→细节

### 第一步：画流程（Flow）

先画出用户从进入到完成核心任务的完整路径。

**核心问题**：
- 用户从进入产品到完成核心任务，需要经过哪些步骤？
- 每步需要什么信息？能做什么操作？
- 异常流程怎么处理？（错误、取消、超时）

**不变原则**：
- 核心操作 3 步内完成——超过 3 步就简化
- 每个操作必须有反馈（成功/失败/进行中）
- 错误处理 > 错误预防（用户犯错时要有明确的恢复路径）

### 第二步：定结构（Structure）

流程画完后，信息架构自然浮现。

**核心问题**：
- 产品有哪些核心概念？（任务、项目、用户、团队）
- 这些概念之间的关系是什么？
- 用户怎么在概念之间导航？

**不变原则**：
- 信息架构要反映用户的心智模型（不是技术模型）
- 导航层级不超过 3 层
- 核心概念要有独立入口（不要藏在深层菜单里）

### 第三步：选模式（Pattern）

从已有交互模式中选择合适的组合，而不是每个页面从零设计。

**核心问题**：
- 哪些交互模式会重复出现？（列表、表单、弹窗、卡片）
- 这些组件需要哪些变体？
- 组件之间的组合规则是什么？

**不变原则**：
- 组件复用 > 定制开发
- 组件要有明确的职责边界（一个组件只做一件事）
- 组件组合要有规则（不是任意组合）

### 第四步：补细节（Detail）

交互设计的质量藏在细节里——反馈、加载、空状态。

**核心问题**：
- 操作反馈用什么形式？（Toast、Modal、Inline）
- 加载状态怎么展示？（骨架屏、Spinner、进度条）
- 空状态怎么展示？（引导、占位图、CTA）

**不变原则**：
- 反馈要及时（操作后 100ms 内）
- 加载状态要减少焦虑（告诉用户"正在做什么"）
- 空状态是机会（引导用户下一步行动）

## AI 的角色

| 阶段 | AI 角色 | 行为 |
|------|---------|------|
| 流程 | 流程审查者 | 搜索同类产品的最佳交互流程，发现遗漏的异常路径 |
| 结构 | 模式研究员 | 搜索信息架构最佳实践，推荐导航模式 |
| 模式 | 组件推荐者 | 搜索交互模式库，推荐适合的组件组合 |
| 细节 | 边界检查者 | 从流程推导边界情况（空状态、错误、权限不足） |

## 决策点

### I1: 用户流程（流程阶段）

**问**：核心任务需要几步？每步需要什么信息和操作？异常怎么处理？

**记录**：用户流程图 + 每步信息需求 + 异常处理

### I2: 信息架构（结构阶段）

**问**：核心概念有哪些？概念之间什么关系？用户怎么导航？

**记录**：信息架构图 + 概念关系 + 导航结构

### I3: 页面布局（结构阶段）

**问**：每个页面展示哪些信息？主次关系？页面间跳转关系？

**不变原则**：每个页面只有一个主要目标 · 主要信息占据视觉中心 · 跳转路径要明确

**记录**：页面线框图 + 信息层级 + 跳转关系

### I4: 组件复用（模式阶段）

**问**：哪些交互模式重复出现？需要哪些变体？组合规则是什么？

**记录**：组件清单 + 变体定义 + 组合规则

### I5: 交互细节（细节阶段）

**问**：反馈形式？加载状态？空状态？

**记录**：反馈规则 + 加载状态 + 空状态设计

## 引导技巧

**4 种技巧**：流程简化（"能不能合并步骤？"）· 异常穷举（"网络断了？数据为空？权限不足？"）· 模式匹配（"用什么现成组件能解决？"）· 空状态设计（"第一次打开看到什么？"）

## 文档约束

**interaction-spec.md 必须包含**：用户流程图（核心+异常）· 信息架构图 · 页面线框图 · 组件清单（行为+组合）· 交互细节 · 响应式策略

**不应包含**：视觉设计（fe-system）· 技术实现（/detail）· 组件外观（fe-system）

## 模板

使用 `${CLAUDE_SKILL_DIR}/references/interaction-template.md` 作为产出结构参考。核心结构：
1. **流程图** — 步骤 × 页面 × 用户操作 × 系统反馈 × 异常处理
2. **信息架构图** — 核心概念 + 关系 + 导航层级
3. **页面线框** — ASCII 线框 + 交互说明
4. **组件复用清单** — 组件名 × 用途 × 来源

## 入口/出口条件

**入口**：有 PRD.md（来自 /define）或用户已有明确需求
**出口**：interaction-spec.md 已生成 · 用户流程已定义 · 信息架构已明确 · 用户确认进入 fe-system 或 /detail

## 何时不使用

- 纯后端 API（没有用户界面）
- 已有完整交互设计（直接进入 fe-system）
- 小功能迭代（简化交互流程）

## 红旗清单

- 核心操作超过 3 步 → 强制简化（"能不能合并步骤？"）
- 没有异常流程 → 强制补充（"出错了怎么办？"）
- 组件复用率低 → 强制抽象（"哪些交互模式重复出现？"）
- 信息架构超过 3 层 → 强制扁平化（"能不能减少层级？"）
- 没有空状态设计 → 强制补充（"第一次使用时展示什么？"）
- 和 fe-system 职责重叠 → 拉回（"这是行为还是外观？"）

## 验证清单

- [ ] 核心流程是否在 3 步内完成？
- [ ] 是否有异常流程（错误、取消、超时）？
- [ ] 信息架构是否反映用户心智模型？
- [ ] 导航层级是否不超过 3 层？
- [ ] 组件复用是否充分？
- [ ] 是否有反馈、加载、空状态设计？
- [ ] 响应式策略是否明确？
