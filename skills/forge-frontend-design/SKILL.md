# Frontend Design — 决策协议

## 职责

引导人类完成前端设计的 5 个决策点。

**原则**：Skill 只问业务问题。技术问题模型自己搜索、自己评估。

每个决策点：
1. 问业务问题（只有人类能回答的）
2. 根据回答，搜索最新技术方案，生成 2-3 个选项 + 各自代价
3. 给出推荐 + 理由
4. 等人类确认
5. 记录选择 + 理由 + 被拒方案

## 产出结构

```
docs/features/<feature>/frontend/
├── contract.md          # F1-F5 决策 + 技术选型 + 共享约束（~80 行）
├── modules/
│   └── <page>.md        # 每个页面/组件一个文件（100-200 行）
└── changelog.md
```

## 方法论：组件驱动设计

前端设计的核心方法论：

1. **页面拆解** — 把页面拆成组件树，每层职责单一
2. **数据流明确** — 区分服务端状态（来自 API）和客户端状态（UI 交互）
3. **约束一致性** — 样式、交互、错误处理在整个产品中保持一致

每个决策点都是这套方法论的一个切面。

## 决策点

### F1: 框架

**问人类：**
- 团队最熟悉什么前端技术？
- 需要搜索引擎能直接抓到页面内容吗？（SEO）
- 这个项目会长期维护还是短期验证？
- 有没有公司级的技术约束？（比如必须用某个框架）

**不变原则：**
- 团队经验 > 技术先进性（团队能维护的才是最好的）
- SEO 需求决定是否必须 SSR/SSG
- 框架选择一旦确定，迁移成本极高，慎重选择

**记录**：框架 + 版本 + 构建工具 + 选择理由 + 被拒方案

---

### F2: 状态管理

**问人类：**
- 有多少数据需要在多个页面/组件间共享？
- 这些数据主要来自 API 还是用户操作？
- 有没有需要撤销/重做的操作？

**不变原则：**
- 服务端状态和客户端状态是不同的东西，不要混在一起
- 服务端状态（API 数据）用缓存/请求库管理
- 客户端状态（UI 状态）用状态管理库管理
- 状态越少越好，能局部就不要全局

**记录**：方案 + 全局状态清单预估 + 选择理由 + 被拒方案

---

### F3: 样式方案

**问人类：**
- 有设计稿或设计系统吗？
- 需要支持暗色模式 / 多主题吗？
- 团队更擅长写 CSS 还是更擅长写 JS？

**不变原则：**
- 样式隔离 > 样式复用（组件间不应该互相影响）
- 设计系统存在时，样式方案必须能消费 Design Token
- 运行时有开销的方案在大规模应用中会成为瓶颈

**记录**：方案 + 设计 token 来源 + 选择理由 + 被拒方案

---

### F4: 数据请求

**问人类：**
- 大概有多少个 API 调用？
- 需要实时数据推送吗？（比如聊天、通知）
- 用户能接受看到旧数据吗？还是每次必须是最新的？

**不变原则：**
- API 调用越多，越需要统一的请求/缓存/重试机制
- 手写 fetch 在项目变大后会失控
- 实时数据需要独立的通信通道，不能用轮询解决

**记录**：方案 + 缓存策略 + 选择理由 + 被拒方案

---

### F5: 表单方案

**问人类：**
- 大概有多少个表单？
- 有动态增减字段的表单吗？（比如：添加多个收件人）
- 表单验证规则需要和后端共享吗？

**不变原则：**
- 表单是前端最复杂的部分之一，不要低估
- 验证规则共享能消除前后端不一致
- 非受控组件在大量表单字段时性能远好于受控组件

**记录**：方案 + 共享 schema 来源 + 选择理由 + 被拒方案

## 文档约束

产出必须包含：
1. **F1-F5 决策**：每个选择 + 理由 + 被拒方案
2. **技术选型表**：所有依赖 + 版本
3. **共享约束**：性能 + 可访问性
4. **模块索引**：每个页面/组件一个 module 文件

### 模块文件格式

每个页面/组件交付：
```
# <PageName> 模块

## 需求
## 验收条件
## 页面结构（组件树）
## 数据流（hooks / queries / mutations）
## 状态管理（store，如有）
## 表单（schema，如有）
## 模块特有约束
```

## 恒久约定

### 组件规范
- 文件名：PascalCase
- 导出：named export
- Props：类型定义与组件同文件

### 目录结构
```
src/
├── components/     # 可复用组件
├── pages/          # 页面组件（路由级）
├── hooks/          # 自定义 hooks
├── stores/         # 状态 stores
├── lib/            # 工具函数
└── types/          # 共享类型（从 api/ 复用）
```

## 入口/出口条件

**入口条件**：
- 有 project.md（来自 /forge-init）
- 有 PRD.md（来自 /forge-define）
- 有 interaction-spec.md（来自 /forge-design）
- 或用户已有技术选型、需求和交互设计（跳过前置阶段）

**出口条件**：
- 生成了 frontend/contract.md（F1-F5 决策完整）
- 每个页面/组件有 modules/*.md
- 技术选型表已填写
- 共享约束已明确（性能 + 可访问性）
- 用户确认是否继续（进入 /forge-plan 

## 何时不使用

- 纯后端 API（没有前端）
- 已有完整的前端详设（直接进入 /forge-plan 
- 简单管理后台（可简化决策流程）

## 红旗清单

- 没有选择理由 → 强制补充（"为什么选这个框架？被拒方案是什么？"）
- 服务端状态和客户端状态混在一起 → 强制分离（"哪些数据来自 API？哪些是 UI 状态？"）
- 没有设计系统但选了运行时 CSS 方案 → 强制评估（"样式怎么保持一致？"）
- 表单数量多但没有表单方案 → 强制补充（"表单验证怎么做？"）
- 没有数据请求策略 → 强制评估（"API 调用怎么缓存？怎么重试？"）

## 验证清单

- [ ] F1-F5 是否都有选择 + 理由 + 被拒方案？
- [ ] 服务端状态和客户端状态是否分离？
- [ ] 样式方案是否能消费 DESIGN.md 的 Design Token？
- [ ] 每个页面/组件是否有对应的 module 文件？
- [ ] 组件树是否清晰（每层职责单一）？
- [ ] 数据流是否明确（hooks / queries / mutations）？
- [ ] 是否有性能约束（首屏加载、交互响应）？
