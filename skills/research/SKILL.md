# Research — 技术探索阶段
## 职责
把"我想做一个壁虎"翻译成"你需要解决这 5 个技术子问题，每个有 3 种算法可选"。
**核心洞察**：人类擅长定义产品愿景（做什么），不擅长识别技术可能性（怎么做）。research 补的就是这个缺口——它不替人做选择，而是把选择空间展开到人面前。
**方法论**：拆解 → 上下文 → 搜索 → 菜单。
## 与上下游的边界
**上游**：define 的 PRD（用户故事 + 验收条件中隐含的技术信号）
**下游**：technical-design 读取 research-brief.md，做架构层面的技术选型
**和 define 的切法**：
- define 关心**用户层面**（用户看到什么、做什么操作）
- research 从用户故事中**提取技术信号**（"平滑爬墙"→ 脊柱算法、"实时同步"→ CRDT vs OT）
**和 technical-design 的切法**：
- research 展开**算法层**（脊柱运动用什么算法？步态控制怎么做？路径规划选哪个？）
- technical-design 收敛**架构层**（单体/微服务、技术栈、部署架构）
research 回答"有哪些算法可选"，technical-design 回答"选哪个组合"。
## 方法论：四阶段
### 第一阶段：问题拆解（Decompose）
把产品愿景分解为独立的技术子问题。每个子问题对应一个技术挑战，可以独立寻找算法方案。
**核心问题**：
- 实现这个产品需要解决哪些技术子问题？
- 哪些子问题是显而易见的？哪些是隐藏的？
- 子问题之间的依赖关系是什么？
**不变原则**：
- 从产品愿景推导技术子问题，不是从技术出发
- 每个子问题要独立到可以单独搜索算法
- 粒度由复杂度决定——简单问题 2-3 个子问题，复杂问题 5-8 个
- 拆得越细，越容易找到对应算法；但过细会增加噪音
### 第二阶段：上下文注入（Context）
算法好坏取决于上下文。从已有项目文档中提取约束，为后续搜索提供评估框架。
**核心问题**：
- 运行平台是什么？（WebGL / 原生 / 嵌入式 / 云端）
- 性能要求是什么？（观赏级 / 工程级 / 仿真级）
- 团队技术背景是什么？（决定了学习成本的上限）
- 有哪些已有约束？（project.md 的技术选型、已有代码库）
**不变原则**：
- 脱离上下文的算法推荐是噪音——同一个算法在不同平台表现相反
- 性能要求决定算法级别——"观赏级壁虎"和"仿真级机器人"用的是完全不同的算法
- 团队背景决定可行性——没有图形学背景的团队不应首选自研渲染引擎
### 第三阶段：算法搜索（Search）
为每个子问题搜索 2-3 个算法方案。使用 web search 获取最新信息——训练数据可能过时。
**核心问题**：
- 这个子问题有哪些成熟算法？
- 各算法在你的上下文里表现如何？
- 有没有现成的参考实现？
**不变原则**：
- 必须用 web search——训练数据中的算法可能过时，开源生态变化快
- 搜索范围：学术论文 + 开源实现 + 社区讨论
- 优先推荐有活跃社区和参考实现的算法
- 纯学术论文标注为"研究阶段"，有 demo 的标注为"可验证"
### 第四阶段：菜单呈现（Menu）
按子问题组织算法菜单。每个算法用统一卡片格式呈现，包含上下文评估。
**核心问题**：
- 每个算法在你的上下文里表现如何？
- 实现复杂度、学习曲线、社区成熟度？
- 哪些算法是互斥的？哪些是互补的？
**不变原则**：
- 菜单是给人看的，不是给机器看的——用人话描述，不堆术语
- 每个算法一句话解释"它解决什么问题"，让不懂算法的人也能做选择
- 标注组合建议——"A 和 B 必须搭配使用"、"C 和 D 是互斥的"
- 探索性组合要诚实标注——"这个组合没人验证过，是创新方向"
## AI 的角色
| 阶段 | AI 角色 | 行为 | 例子 |
|------|---------|------|------|
| 拆解 | 技术分解者 | 从产品愿景推导技术子问题 | "壁虎爬墙需要：脊柱运动、四肢步态、表面贴合、路径规划" |
| 上下文 | 约束提取者 | 从 project.md 提取平台、性能、团队约束 | "WebGL + 60fps + 无图形学背景 = 排除自研物理引擎" |
| 搜索 | 算法搜索者 | web search 搜索算法方案、参考实现、社区评价 | "IK 算法有三种主流实现，Three.js 生态有 ready-made 库" |
| 菜单 | 翻译者 | 把算法术语翻译成产品语言，标注推荐度 | "Catmull-Rom = 简单平滑，适合观赏级；IK = 真实但复杂" |
## 决策点
### R1: 子问题拆解
**问**：实现这个产品需要解决哪些技术问题？渲染、动画、交互、物理、性能各有什么挑战？
**记录**：子问题清单（编号 SP1-SPn）+ 每个子问题一句话描述 + 子问题间的依赖关系
### R2: 算法搜索（每个子问题重复）
**问**：这个子问题有哪些成熟算法？各算法在你的上下文里表现如何？
**不变原则**：必须 web search · 优先推荐有参考实现的 · 纯论文标注"研究阶段"
**记录**：算法卡片（名称 + 一句话 + 上下文评估 + 复杂度 + 成熟度 + 参考链接）
### R3: 组合建议
**问**：哪些算法必须搭配使用？哪些是互斥的？推荐的组合是什么？
**不变原则**：标注已验证组合 vs 探索性组合 · 诚实标注风险
**记录**：推荐组合 + 耦合关系 + 风险标注
### R4: 可行性评估
**问**：最难实现的子问题是哪个？最高风险是什么？需要原型验证吗？
**不变原则**：最高风险子问题优先验证 · 原型 < 完整实现
**记录**：风险评估 + 验证计划（哪些子问题需要 POC）
## 引导技巧
**4 种技巧**：类比翻译（"IK 就像你拉一根绳子，末端跟着目标走"）· 菜单思维（"你只需要选，不需要懂公式"）· 诚实标注（"这个组合是探索性的，没人在生产环境验证过"）· 旋钮暴露（"这个算法的精度参数可以调，当前推荐默认值"）
**深入信号**：用户开始追问某个算法的细节、问"能不能两个都用"
**前进信号**：用户对每个子问题都做了选择、组合关系明确
## 文档约束
**research-brief.md 必须包含**：子问题分解（SP1-SPn）+ 每个子问题的算法卡片 + 组合建议 + 风险评估 + 验证计划
**research-brief.md 不应包含**：架构决策（technical-design 阶段）· 技术栈选择（technical-design 阶段）· 具体 API 设计（detail 阶段）· 代码（codegen 阶段）
## 模板
使用 `${CLAUDE_SKILL_DIR}/references/research-brief-template.md` 作为产出结构参考。
research-brief.md 的三个核心结构（详见模板）：
1. **子问题地图** — SP# × 描述 × 依赖关系 × 难度评估
2. **算法菜单** — 按子问题组织，每个算法一张卡片
3. **组合建议** — 推荐组合 + 耦合关系 + 探索性标注
## 入口/出口条件
**入口**：PRD 已完成（来自 define 阶段），用户故事中包含技术信号词（实时、平滑、同步、搜索、推荐、动画等）
**出口**：生成 research-brief.md + 每个子问题有算法菜单 + 组合建议 + 用户确认进入 technical-design 阶段
## 运行时信号
- 输入：PRD technical signals
- 输出：algorithm menu、technical recommendation
- 路由：详见 `registry.yaml` 的 `forge-research` 节点；本节只保留人类可读摘要。
- 升级：技术信号词存在但没有可行方案 · 所有方案都有重大 trade-off
## 何时不使用
- 纯 CRUD 应用（表单→数据库→列表页，没有技术选择空间）
- 用户已经给出完整技术方案（"用 X 框架 + Y 算法 + Z 数据库"）
- 团队刚做完类似项目，子问题和方案都很清楚
## 红旗清单
- 子问题太少（< 3）→ 追问隐藏的技术挑战（"渲染、动画、交互、性能各有什么难点？"）
- 所有算法都很前沿 → 标注风险 + 推荐降级方案（"如果追求观赏级而非仿真级，这些更简单"）
- 没有 web search 能力 → 标注"基于训练数据，可能过时" + 建议手动验证
- 算法组合未经验证 → 诚实标注"探索性组合" + 建议原型验证
- 用户看不懂算法卡片 → 换类比，直到用户能说"我选这个"
## 验证清单
- [ ] 子问题是否覆盖了产品的所有技术挑战？
- [ ] 每个子问题是否有 ≥ 2 个算法选项？
- [ ] 算法卡片是否包含：名称、一句话、上下文评估、复杂度、成熟度、参考链接？
- [ ] 是否基于 project.md 的上下文做了评估（不是脱离上下文的通用推荐）？
- [ ] 是否有组合建议 + 耦合关系标注？
- [ ] 是否有风险评估 + 验证计划？
- [ ] 是否用了 web search（不是纯靠训练数据）？
- [ ] 用户是否能看懂每个算法"解决什么问题"（不堆术语）？
