# Brainstorm — 探索阶段

## 职责

引导用户在模糊阶段展开可能性空间，从"想做个东西"到"这个方向值得深入"。

**原则**：先发散再收敛。发散阶段不评判、不决策、不承诺。

## 决策点

### B1: 痛点探索

**问**：
- 当前用户怎么解决这个问题的？
- 现有方案最让人头疼的是什么？
- 如果只能解决一个痛点，解决哪个？

**不变原则**：
- 痛点要具体到能讲出一个真实的场景（不是"效率低"，是"每周花 3 小时手动复制数据"）
- 先理解问题再想方案——跳到方案太快是 brainstorm 最常见的失败
- 用户说的痛点和真正的痛点经常不一样——追问"为什么"直到触达根因

**AI 辅助**：搜索现有竞品怎么解决这个问题、行业报告中的痛点排名

**记录**：核心痛点 + 现有方案 + 改进空间

### B2: 可能性展开

**问**：
- 想过哪些方向来解决这个问题？
- 有没有参考的产品或方案？
- 如果没有任何技术限制，理想的方案是什么？

**不变原则**：
- 发散阶段不评判——"这个不行"留到 B3 再说
- 至少 3 个方向，包含至少 1 个"看起来疯狂"的选项
- 每个方向要有"什么场景下它是对的"——没有绝对的好坏，只有适用场景

**AI 辅助**：搜索同类产品、类似问题的创新解法、技术方案可行性，补充用户没想到的方向

**记录**：方向列表（3-5 个）+ 各自的核心思路

### B3: 方向评估

**问**：
- 这些方向各自解决哪些痛点？
- 哪个方向最符合团队的能力？
- 哪个方向最容易验证？

**不变原则**：
- 评估标准先于评估——先定标准，再打分，避免凭感觉
- 不找"最好的"，找"最适合当前条件的"
- 被拒方向要记录理由——未来条件变化时可能重新启用

**AI 辅助**：搜索选定方向的成功案例和常见失败原因

**记录**：方向对比矩阵 + 推荐方向 + 推荐理由

### B4: 边界探索

**问**：
- 这个方向有哪些变体？
- 哪些功能是核心，哪些是锦上添花？
- 如果只能做一个功能，做哪个？

**不变原则**：
- MVP 是"去掉任何一个就不成立"的最小集合
- 边界比功能重要——说"不做什么"比说"做什么"更有价值
- 每个边界声明都要有理由

**记录**：核心功能清单 + 边界声明 + MVP 定义

### B5: 下一步行动

**问**：
- 需要验证哪些假设？
- 谁来决定是否继续？
- 验证成功后的下一步是什么？

**不变原则**：
- 探索不验证 = 没探索——每个方向至少有一个可验证的假设
- 验证要便宜且快速——访谈 > 原型 > 完整产品
- 决策标准提前定——"什么情况下继续、什么情况下停止"

**记录**：假设清单 + 验证计划 + 决策标准 + 下一步行动

## 引导流程

### 发散→收敛节奏

- 前 60% 时间发散：展开可能性，不评判
- 后 40% 时间收敛：评估方向，圈定 MVP
- 信号：至少 3 个方向展开后才开始收敛
- 技巧：用"如果只能选一个"强制收敛，用"什么条件下它是对的"验证判断

### 引导技巧

| 技巧 | 用法 | 场景 |
|------|------|------|
| 5 Whys | 追问 5 层"为什么" | 找到根本痛点（B1） |
| 极端场景 | "如果用户是 1 个人？100 万人？" | 打开思路（B2） |
| 类比思维 | "其他行业怎么解决类似问题的？" | 跨领域借鉴（B2） |
| 反转思维 | "什么方案一定会失败？" | 反推正确做法（B3） |
| 约束加减法 | "如果预算无限？如果只有 1 周？" | 探索不同约束下的方案（B2-B4） |

## AI 辅助研究

AI 不只是被动回答，要主动搜索扩展可能性空间：

| 阶段 | AI 搜索 | 目的 |
|------|---------|------|
| B1 | 竞品分析 + 现有方案 | 了解市场格局 |
| B2 | 类似产品 + 技术方案 + 最佳实践 | 补充用户没想到的方向 |
| B3 | 选定方向的成功案例 + 失败教训 | 提供评估依据 |

## 文档约束

**idea-brief.md 必须包含**：核心痛点 · 方向地图（3-5 个）· 推荐方向+理由 · MVP 定义 · 假设清单+验证计划 · 决策标准 · 下一步行动

**idea-brief.md 不应包含**：技术选型（/forge-init）· 详细功能列表（/forge-define）· 交互设计（/forge-design）· 代码（生成代码）

## 模板

使用 `${CLAUDE_SKILL_DIR}/references/idea-brief-template.md` 作为产出结构参考。

idea-brief.md 的三个核心结构（详见模板）：
1. **方向对比矩阵** — 方向 × 维度（核心思路、适用场景、风险、验证难度）
2. **MVP 定义** — 核心功能 + 边界声明 + 验证标准
3. **假设清单** — 假设 × 验证方法 × 成功标准 × 负责人 × 时间

## 入口/出口条件

**入口条件**：
- 用户有一个模糊的想法或痛点
- 尚未明确具体方向

**出口条件**：
- 生成了 idea-brief.md
- 有明确的推荐方向 + 理由
- 有可执行的验证计划
- 用户确认是否继续（进入 /forge-init）

## 何时不使用

- 方向已经明确（跳过 brainstorm，直接进入 /forge-init）
- 只是技术实现问题（直接进入 /forge-detail）
- 已有完整的 PRD（直接进入 /forge-design）

## 红旗清单

- 用户说"我们想做一切" → 强制收敛到 1 个核心痛点（"发散之前先定焦点"）
- 所有方向都"差不多" → 强制排序（"如果只能选一个呢？"）
- 用户跳过发散直接收敛 → 拉回发散，至少展开 3 个方向
- 过早评判 → 制止（"发散阶段先记下来，评估时再判断"）
- 痛点太抽象 → 追问具体例子（"能描述一个真实的场景吗？"）
- 没有验证计划 → 补充（"怎么知道这个方向是对的？"）
- MVP 太大 → 砍到"没有它就不成立"的最小集合
- 所有方向都很常规 → 加 1 个疯狂选项（"如果预算无限，你会怎么做？"）

## 验证清单

- [ ] 痛点是否具体到能讲出真实场景？
- [ ] 是否展开了至少 3 个方向？
- [ ] 每个方向是否有"什么场景下它是对的"？
- [ ] 是否有方向对比矩阵 + 推荐方向 + 理由？
- [ ] MVP 是否小到可以在 2 周内验证？
- [ ] 是否有可执行的验证计划？
- [ ] 是否有明确的决策标准（继续/停止）？
- [ ] 下一步行动是否具体到"谁、做什么、什么时候"？

## 历史维护（自动）

完成后自动执行，不需要人工触发：

1. **追加 docs/timeline.md**（如不存在则创建）：
   ```markdown
   ### {日期} — {主题} 探索
   - 产出：idea-brief.md（{N} 个方向，推荐：{方向名}）
   ```

2. **检查膨胀**：timeline.md 超过 100 行时，旧记录归档到 `timeline/`。
