# Plan — 任务阶段

## 职责

把详设文档拆成可执行的任务序列——每个任务是一个完整、可独立验证的用户价值交付。

**核心洞察**：好的任务分解不是按技术层切（先写所有 schema，再写所有 route），而是按用户价值切（一个任务 = 一个完整功能路径）。垂直切片保证每个任务都能独立交付和验证，避免"写了一周代码但什么都不能用"。

**方法论**：识别 → 切片 → 排序 → 验证 → 检查 → 测试推导。

## 执行纪律

- **D4**：垂直切片不水平分层，每个任务是完整的用户价值
- **D7**：每个任务必须有验证标准，验证从 contract.md 验收条件推导
- **D5**：只分解任务和排序，不涉及具体实现（codegen）

## 与上下游的边界

**上游**：读 contract.md + modules/（来自 detail 阶段），知道有哪些模块和接口合约
**下游**：plan.md 交给代码生成（按任务序列生成 src/ + tests/）· 从验收条件自动推导 testing/test-cases.md（详见 test-cases skill）

**和 detail 的切法**：detail 定义**做什么**（合约+模块），plan 定义**怎么做**（任务+顺序）
**和 codegen 的切法**：plan 定义**任务序列**（目标+步骤+验证），codegen 定义**具体实现**（代码）

> Plan 使用 PL# 前缀（Plan Decision）。PL# 记录在 plan.md 中。仅用于关键规划决策（如任务拆分争议、风险优先级判断），不用于每个任务的步骤。

## 方法论：识别→切片→排序→验证→检查

### P1: 识别（Identify）

读 contract.md + modules/，建立模块全景。不知道有什么就切不好。

**核心问题**：有哪些模块？每个模块包含哪些端点/组件？模块间依赖是什么？哪些是共享基础设施？

**不变原则**：
- 先画全景再切片——模块依赖图是切片的基础
- 共享基础设施（中间件、工具函数、数据库 schema）要单独识别，它们通常是第一批任务
- 高风险/技术不确定的模块要标记——先验证最不确定的部分，降低后期返工

**记录**：模块清单 + 依赖图 + 风险标记

### P2: 切片（Slice）

把每个模块拆成垂直切片——每个切片是一个完整、可独立验证的用户价值。

**核心问题**：这个模块有哪些用户路径？每个路径的入口和出口是什么？切片能独立验证吗？

**不变原则**：
- 垂直切片不水平分层——"建所有 DB"是反模式，"创建任务 API（含 schema+route+test）"是正模式
- 切片是**完整的用户价值**——不一定穿三层（schema→API→UI），但必须从入口到出口可运行
- 每个任务 3-7 步 · 涉及 ≤ 5 个文件
- 做减法是艺术——超过 7 步先问"能不能拆成两个独立可验证的路径？"
- 禁止占位符（TBD/TODO/后续补充）——写不出步骤说明没想清楚

**引用而非复述**：任务描述中的约束、数据模型、接口定义引用 contract.md（FD# / 模块名），不复述内容。
- ❌ "guard 校验路径 sandbox + 像素限制 100MP + tile 限制 64 + 源文件保护"
- ✅ "实现 guard 校验逻辑（约束见 contract.md FD4 + project.md PD3）"
- 任务步骤中需要具体参数/字段时，引用模块文件而非复制数据模型

**PRD 来源追溯**：每个任务标注对应的 PRD 用户故事和验收条件：
```markdown
### Task-03: inspect 命令
**PRD 来源**：US-01（AC-01-1, AC-01-2, AC-01-3）
**目标**：...
```

**记录**：任务清单（目标 + PRD 来源 + 文件 + 步骤）

### P3: 排序（Order）

确定任务间的依赖关系、执行顺序和风险优先级。

**核心问题**：哪些任务有数据依赖？哪些共享文件（不能并行）？关键路径是什么？哪些任务风险最高？

**不变原则**：
- 依赖关系 = 数据依赖（一个任务的输出是另一个的输入）
- 并行条件 = 无共享文件 + 无数据依赖
- 关键路径决定最短完成时间——优化关键路径上的任务优先
- 高风险/高不确定性任务优先排——先做最不确定的部分（"先验证风险，再填充功能"）
- 拓扑排序保证执行时不会"用到还没写的东西"

**记录**：拓扑顺序 + 并行矩阵 + 关键路径 + 风险排序

### P4: 验证（Verify）

为每个任务定义验证标准。有业务逻辑的任务用 TDD，其他用验收条件直接验证。

**核心问题**：怎么知道这个任务做对了？这个任务适合 TDD 还是直接验证？

**不变原则**：
- 没有验证标准 = 任务不存在——"怎么知道做对了？"是必须回答的问题
- 验证标准从 contract.md 的验收条件推导，不是凭空编的
- **TDD（RED → GREEN → REFACTOR）** 适用于：有业务逻辑的 API、复杂数据处理、核心算法
- **直接验证**适用于：数据库迁移、配置文件、CI pipeline、纯 UI 样式、依赖安装
- 每个有业务逻辑的任务至少有一个端到端验证（不只是单元测试）

**记录**：每任务验证方式（TDD 或直接验证）+ 验收条件

### P5: 检查（Checkpoint）

在关键节点设置人工审查门。

**核心问题**：哪些任务完成后需要人工审查？审查不通过怎么办？

**不变原则**：
- 不是每个任务都需要审查——只在关键架构决策、复杂业务逻辑、跨模块集成时设检查点
- 检查点有明确验收标准（不是"看看对不对"）
- 检查点不通过 = 修复后重新检查，不跳过

**记录**：检查点清单 + 验收标准 + 回退方案

### P6: 测试推导（Test Derivation）

从验收条件和验证方式自动推导测试用例骨架。

**核心问题**：哪些任务适合自动生成测试用例？哪些只能手动验证？

**不变原则**：
- TDD 任务：从验收条件推导测试用例骨架（测试名 + 输入 + 预期输出）
- 直接验证任务：标记为"手动验收"，不生成自动化用例
- 推导结果写入 `testing/test-cases.md`（测试范围矩阵 + P0 用例清单）
- 完整测试策略由 `test` 编排 skill 负责，此处只做自动推导

**记录**：testing/test-cases.md（测试范围矩阵 + 用例骨架）

**与 test-cases 的分工**：plan P6 只产出测试范围矩阵 + P0 用例骨架（≤ 30 行）。完整测试用例（正常/边界/错误/数据）由 test-cases skill 负责。如果用户需要完整测试用例，plan 的完成提示中推荐进入 test 阶段。

## AI 的角色

| 阶段 | AI 角色 | 行为 |
|------|---------|------|
| 识别 | 模块分析师 | 读 contract.md，画模块依赖图，识别共享基础设施和风险点 |
| 切片 | 切片设计师 | 拆成垂直切片，确保每个切片是完整用户价值 |
| 排序 | 依赖规划者 | 确定拓扑顺序、并行机会、关键路径、风险优先级 |
| 验证 | 验证定义者 | 从验收条件推导验证方式（TDD 或直接验证） |
| 检查 | 风险识别者 | 在关键节点设检查点，定义审查标准 |
| 测试推导 | 测试映射者 | 从验收条件推导测试用例骨架，区分 TDD 和手动验证 |

## 引导技巧

**切片判断**："这个任务是按技术层切的还是按用户路径切的？"
**粒度判断**："这个任务 3-7 步能完成吗？不能就拆。"
**验证判断**："怎么知道做对了？说不清楚就是没想好。"
**并行判断**："这两个任务共享文件吗？共享就不能并行。"
**风险判断**："哪个任务最可能出问题？应该先做它。"

## 文档约束

**plan.md 必须包含**：模块依赖图 · 任务清单（目标+文件+步骤+验证） · 拓扑排序 · 并行矩阵 · 关键路径 · 风险标记 · 检查点 · 验证方式
**plan.md 不应包含**：具体代码实现（codegen）· 具体测试用例（test-cases）· 部署步骤（deploy）

**plan.md 路径**：`docs/features/<feature>/plan.md`

## 模板

使用 `${CLAUDE_SKILL_DIR}/references/plan-template.md` 作为产出结构参考（含任务格式、依赖图格式、并行矩阵格式、检查点格式）。

## 入口/出口条件

**入口**：有 contract.md + modules/（来自 detail 阶段）或用户已有详设文档

**缺失处理**：contract.md 不完整 → 只切已有模块，标注"待补模块"；modules/ 为空 → 从 contract.md 推导最小切片。

**出口**：plan.md 已生成 · testing/test-cases.md 已生成（P6 从验收条件 + 验证方式推导） · 用户确认进入代码生成

## 运行时信号

- 输入：domain contracts
- 输出：task sequence、checkpoints
- 路由：详见 `registry.yaml` 的 `forge-plan` 节点；本节只保留人类可读摘要。
- 升级：任务无法垂直切片 · 验收标准缺失

## 何时不使用

只有一个模块（不需要分解）· 已有明确任务清单 · 小功能迭代（简化流程）

## 红旗清单

- 任务超过 7 步 → 强制拆分
- 任务涉及超过 5 个文件 → 强制拆分
- 水平切片（"建所有 DB"） → 强制垂直切片（"一个用户路径是什么？"）
- 没有验证标准 → 强制补充
- 没有依赖图 → 强制画
- 有占位符（TBD/TODO） → 强制细化
- 所有任务都是串行的 → 强制检查并行机会
- 没有关键路径 → 强制标出
- 高风险任务排在后面 → 强制提前（"先验证最不确定的"）

## 验证清单

- [ ] 任务是否垂直切片（完整可验证的用户价值）？
- [ ] 每个任务是否 3-7 步、≤ 5 个文件？
- [ ] 是否有依赖图 + 拓扑排序 + 并行矩阵 + 关键路径？
- [ ] 每个任务是否有验证方式（TDD 或直接验证）？
- [ ] 是否有检查点（关键节点的人工审查门）？
- [ ] 是否无占位符（TBD/TODO）？
- [ ] 高风险任务是否优先排列？
- [ ] 是否从验收条件推导了 testing/test-cases.md？

## 历史维护（自动）

完成后追加 `docs/timeline.md`：`### {日期} — {feature} 任务分解 · plan.md（{N} 个任务）+ testing/test-cases.md`。追加 `changelog.md`。超 100 行时归档。自动推导测试用例时加载 `test-cases`，但历史由 `plan` 写一条汇总记录，避免重复。

**更新 docs/status.md**：④任务 → `✅`，⑤构建 → `🔄`。如有跳过的阶段，标注 `⏭️跳过（原因）`。

## 完成提示

```
✅ 任务分解完成！plan.md + testing/test-cases.md（用例骨架）已生成。

下一步你可以：
  test 阶段    — 测试策略 + 补全测试用例（Recommended — P6 只产出了用例骨架，测试策略还缺：测试金字塔、Mock 策略、CI 集成）
  生成代码       — 按任务序列生成 src/ + tests/
```

**注意**：deploy 不在 plan 的完成提示里。deploy 的入口条件是「有 src/ + tests/ + testing/test-cases.md，review 通过」，这些在 plan 之后都不存在。deploy 应出现在 codegen 或 test 的完成提示中。
