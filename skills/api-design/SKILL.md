# API Design — 决策协议

## 职责

引导人类完成 API 设计的 7 个决策点。

**原则**：Skill 只问业务问题。技术问题模型自己搜索、自己评估。

每个决策点：
1. 问业务问题（只有人类能回答的）
2. 根据回答，搜索最新技术方案，生成 2-3 个选项 + 各自代价
3. 给出推荐 + 理由
4. 等人类确认
5. 记录选择 + 理由 + 被拒方案

## 产出结构

```
docs/features/<feature>/
├── contract.md          # 共享骨架（~100 行）
├── api/
│   ├── contract.md      # D1-D7 决策 + 共享数据模型 + 技术选型（~120 行）
│   ├── modules/
│   │   └── <module>.md  # 每个模块一个文件（100-200 行）
│   └── changelog.md
```

## 方法论：资源导向设计

API 设计的核心方法论是**资源导向**（Resource-Oriented Design）：

1. **识别资源** — 系统管理哪些核心实体？
2. **建立关系** — 资源之间的从属、引用、组合关系
3. **映射操作** — CRUD 到 HTTP 动词的自然映射
4. **统一接口** — 一致的错误、分页、认证、幂等模式

每个决策点都是这套方法论的一个切面。

## 决策点

### D1: 资源建模

**问人类：**
- 系统管理哪些核心实体？（比如：用户、订单、商品）
- 它们之间的自然关系是什么？（用户有多个订单 = 1:N）
- 有没有实体必须独立存在、不能脱离父实体？

**不变原则：**
- URL 是资源的地址，不是动作的调用
- 嵌套深度 ≤ 2 层，过深用查询参数替代
- 资源名用复数名词

**记录**：资源清单 + 关系图 + 选择理由 + 被拒方案

---

### D2: 分页策略

**问人类：**
- 列表数据大概会增长到多少？
- 用户需要跳到第 N 页吗？还是只需要"加载更多"？
- 数据变化快吗？（实时 feed vs 后台管理）

**不变原则：**
- 无界数据集必须分页，永远不允许 `SELECT *`
- 分页策略由**数据量级 + 访问模式**决定，不由偏好决定
- 跳页和性能是一对矛盾，量级越大越偏向游标

**记录**：选择 + 理由 + 被拒方案 + 默认排序

---

### D3: 错误格式

**问人类：**
- 谁会调用这个 API？（内部团队 / 第三方开发者 / 终端用户前端）
- 有多少个团队会对接这个 API？
- 有行业标准或合规要求吗？

**不变原则：**
- 错误响应必须结构化，不能只返回字符串
- 错误码稳定（程序判断用），错误信息可变（人类阅读用）
- 消费者越多，格式越需要标准化

**记录**：格式 schema + code 规范 + 选择理由 + 被拒方案

---

### D4: 权限失败策略

**问人类：**
- 有没有"不应该让别人知道这东西存在"的场景？（比如：别人的私人数据）
- 系统面向内部还是外部？
- 调试时需要明确的权限错误提示吗？

**不变原则：**
- 403 暴露资源存在性但调试友好
- 404 隐藏资源存在性但调试困难
- 选择取决于**安全等级**，不是偏好

**记录**：策略 + 适用资源分类 + 选择理由 + 被拒方案

---

### D5: 幂等策略

**问人类：**
- 重复执行这个操作最坏会怎样？（重复扣款 vs 重复创建草稿）
- 用户会在不稳定的网络下使用吗？（移动端 / 弱网）
- 有没有业务字段天然可以防重？（订单号、流水号）

**不变原则：**
- 有副作用的写操作必须考虑重复执行
- 副作用越严重，幂等要求越严格
- 有天然幂等键就用，没有就需要外部机制

**记录**：哪些端点需要 + 策略 + 冲突处理 + 选择理由 + 被拒方案

---

### D6: 并发控制

**问人类：**
- 同一个资源会被多人同时修改吗？
- 如果 A 的修改被 B 静默覆盖了，后果严重吗？
- 用户编辑到一半、别人已经改了，用户希望怎么被通知？

**不变原则：**
- 并发冲突的风险由**协作模式**决定，不是技术偏好
- 单人独占资源不需要并发控制
- 多人协作资源必须有机制，否则数据丢失不可追溯

**记录**：哪些资源需要 + 策略 + 冲突处理 + 选择理由 + 被拒方案

---

### D7: 认证方式

**问人类：**
- 系统是单体还是微服务？
- 有没有第三方应用需要调用这个 API？
- 用户会话需要跨设备共享吗？

**不变原则：**
- 认证方式由**系统架构**决定，不是偏好
- 无状态系统 → token 方案
- 有状态系统 → session 方案
- 服务间调用 → API Key / mTLS

**记录**：认证方式 + token 格式 + 过期策略 + 选择理由 + 被拒方案

## 文档约束

产出必须包含四层信息：
1. **WHAT**：功能需求 + 验收条件
2. **WHY**：每个决策的选择 + 理由 + 被拒方案
3. **HOW**：数据模型 + 接口合约 + 技术选型
4. **CONSTRAINTS**：安全 + 性能 + 兼容性

### 接口合约格式

每个端点交付：
```
METHOD /path
  Auth: 认证要求
  Idempotency: 幂等策略（如适用）
  Concurrency: 并发控制（如适用）
  Request: DTO + 字段约束
  Response: 状态码 + DTO
  Errors: error code + HTTP status
  Notes: 补充说明
```

### 命名约定（恒久不变）
- URL: plural nouns（/tasks, /users/:id/orders）
- JSON body: camelCase
- Error code: UPPER_SNAKE_CASE
- 时间: ISO 8601
- ID: string（不暴露数据库自增）
