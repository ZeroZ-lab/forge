# Visual Design — 设计阶段（视觉层）

## 职责

建立视觉语言，让产品在视觉上系统化一致。不是每个页面单独设计，而是建立系统后消费。

**核心洞察**：一致性 > 创意。好的设计系统让新页面"自动"变好看——因为所有选择已经被系统做了。

**方法论**：基调→系统→组件外观→Token 化。

## 与上下游的边界

**上游**：读 interaction-spec（交互规格），知道页面结构和组件行为
**下游**：DESIGN.md 交给 /forge-detail（前端实现）和代码生成

**和 interaction-design 的切法**：
- interaction 定义**组件做什么**（行为、组合规则、交互模式）
- visual 定义**组件长什么样**（外观、色彩、间距、状态样式）

## 方法论：基调→系统→组件外观→Token 化

### 第一步：定基调（Tone）

视觉设计从产品气质开始，不是从色号开始。

**核心问题**：
- 产品的气质是什么？（专业、活泼、极简、温暖、科技感）
- 有品牌指南吗？
- 需要支持暗色模式吗？多平台？

**不变原则**：
- 气质决定色彩和字体的选择方向
- 品牌指南（如果有）是起点，不是约束
- 暗色模式和多平台要从一开始考虑（不是事后补）

### 第二步：建系统（System）

从基调推导出基础三件套：色彩、字体、间距。

**核心问题**：
- 主色是什么？语义色怎么定？中性色体系？
- 字体家族？字体层级（标题/正文/辅助）？行高？
- 间距基准单位？间距层级（组件内/组件间/区块间）？

**不变原则**：
- 主色不超过 3 个（主色、辅助色、强调色）
- 色彩要有语义（成功=绿、警告=黄、错误=红、信息=蓝）
- 对比度要符合 WCAG 标准（文本至少 4.5:1）
- 字体层级要清晰（标题、正文、辅助文本）
- 间距要有规律（4px 基准网格）
- 留白是设计工具，不是浪费

### 第三步：定义组件外观（Component Appearance）

基于系统定义每个组件长什么样。

**核心问题**：
- 每个组件有哪些变体？（primary/secondary/ghost/danger）
- 每个组件有哪些状态？（默认、悬停、聚焦、禁用、加载）
- 尺寸变体有哪些？（small、medium、large）

**不变原则**：
- 组件状态要完整（不要漏掉禁用、加载状态）
- 组件外观从系统 Token 推导（不单独定义颜色）
- 组件尺寸从间距系统推导（不单独定义 padding）

### 第四步：Token 化（Tokenize）

把设计系统变成代码可消费的 Token。

**核心问题**：
- Token 的命名规范是什么？
- 需要支持多主题吗？
- Token 如何与代码同步？

**不变原则**：
- Token 命名要语义化（color-primary 不是 color-blue）
- Token 要分层（全局 Token → 别名 Token → 组件 Token）
- Token 要与代码同步（设计系统 = 单一真相源）

## AI 的角色

| 阶段 | AI 角色 | 行为 |
|------|---------|------|
| 基调 | 气质翻译者 | 把"专业/活泼/极简"翻译成具体的色彩和字体方向 |
| 系统 | 设计系统搜索者 | 搜索行业设计系统（Material、Ant、Chakra），推荐最佳实践 |
| 组件 | 状态检查者 | 检查每个组件是否覆盖了所有状态（默认/悬停/聚焦/禁用/加载） |
| Token | 命名规范者 | 推荐 Token 命名规范和分层结构 |

## 决策点

### V1: 色彩系统（基调+系统阶段）

**问**：有品牌指南吗？产品气质？暗色模式？

**记录**：色板（主色、辅助色、语义色、中性色）+ 暗色模式变体

### V2: 字体系统（系统阶段）

**问**：有品牌字体吗？多语言？字体加载策略？

**不变原则**：行高要舒适（1.5-1.8 倍）· 正文字体至少 14px

**记录**：字体家族 + 字体层级 + 行高规则

### V3: 间距系统（系统阶段）

**问**：产品节奏感？响应式间距？基准单位？

**不变原则**：间距要分层（组件内、组件间、区块间）

**记录**：间距规范（基准单位 + 层级 + 响应式规则）

### V4: 组件库（组件外观阶段）

**问**：需要哪些基础组件？状态？尺寸变体？

**记录**：组件清单 + 状态定义 + 尺寸变体 + 组合规则

### V5: 设计 Token（Token 化阶段）

**问**：命名规范？多主题？与代码同步？

**记录**：Token 结构 + 命名规范 + 同步策略

## 引导技巧

**4 种技巧**：气质具象化（"3 个形容词描述气质"）· 对比度检查（自动计算 WCAG）· 状态穷举（"默认？悬停？聚焦？禁用？加载？"）· Token 分层（"全局/别名/组件级？"）

## 文档约束

**DESIGN.md 必须包含**：色彩系统 · 字体系统 · 间距系统 · 组件库（外观+状态+变体）· 设计 Token · 图标系统 · 动效规范

**DESIGN.md 不应包含**：交互设计（interaction-design）· 具体页面设计（interaction-design）· 代码实现（/forge-detail）

## 模板

使用 `${CLAUDE_SKILL_DIR}/references/design-system-template.md` 作为产出结构参考。核心结构：
1. **色彩系统表** — Token × 值 × 用途
2. **字体层级表** — Token × 大小 × 字重 × 行高 × 用途
3. **间距系统表** — Token × 值 × 用途
4. **组件规范** — 变体 × 尺寸 × 状态

## 入口/出口条件

**入口**：有 interaction-spec.md（来自 interaction-design）或用户已有交互设计
**出口**：DESIGN.md 已生成 · 设计系统已建立 · 设计 Token 已定义 · 用户确认进入 /forge-detail

## 何时不使用

- 纯后端 API（没有用户界面）
- 已有完整设计系统（直接进入 /forge-detail）
- 内部工具不需要精美设计（简化视觉流程）

## 红旗清单

- 主色超过 3 个 → 强制收敛（"哪个是主色？"）
- 对比度不符合 WCAG → 强制调整（"文本至少 4.5:1"）
- 间距没有规律 → 强制使用基准网格（"4px 还是 8px？"）
- 组件状态不完整 → 强制补充（"禁用、加载状态呢？"）
- Token 命名不语义化 → 重写（"color-primary 不是 color-blue"）
- 和 interaction-design 职责重叠 → 拉回（"这是行为还是外观？"）

## 验证清单

- [ ] 色彩系统是否完整（主色、语义色、中性色）？
- [ ] 对比度是否符合 WCAG 标准？
- [ ] 字体层级是否清晰（标题、正文、辅助）？
- [ ] 间距是否有规律（基准网格）？
- [ ] 组件库是否完整（基础组件 + 状态 + 变体）？
- [ ] 设计 Token 是否语义化命名？
- [ ] 是否支持暗色模式（如需要）？
