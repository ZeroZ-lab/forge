# Review — 独立审查

## 职责

用独立的 subagent 审查文档或代码——消除"自己写自己审"的认知偏见。

**核心洞察**：同一个 AI 写文档 + 审查文档 = 同一个偏见投影两次。写的时候觉得"端点设计很完整"，审的时候还是觉得完整——遗漏被同一个认知模型掩盖。独立 subagent 从零读文档，没有写文档时的假设。

**两种模式**：

| 模式 | 触发时机 | 审查什么 | 消费什么 |
|------|---------|---------|---------|
| 文档审查 | codegen 之前 | 上游文档完整性和一致性 | docs/ |
| 代码审查 | deploy 之前 | 代码是否文档的忠实投影 | docs/ + src/ |

**方法论**：打包上下文 → spawn subagent → 独立审查 → 收集报告。

## 与上下游的边界

**上游**：docs/（文档）或 docs/ + src/（文档 + 代码）
**下游**：审查报告交给 detail（补文档）或 codegen（修代码）

**和 codegen 的关系**：codegen 开始前，review 以文档审查模式做交接检查点（subagent 执行）
**和 deploy 的关系**：deploy 开始前，review 以代码审查模式做发布门禁（subagent 执行）

## 核心机制：Subagent 独立审查

### 为什么必须用 subagent

```
自审的盲区：
  codegen 读 contract → "需要 cursor 分页" → 实现 cursor
  同一个 AI 审查 → 还是认为 cursor 正确 → 如果 contract 写的是 page → 分歧被掩盖

Subagent 的优势：
  1. 全新视角——没有写文档时的认知偏见
  2. 上下文隔离——对话历史的假设不带入
  3. 文档驱动——如果文档不够清晰让新 agent 理解，文档本身就有问题
```

### 主 Agent 职责（编排）

```
1. 确定审查模式（文档审查 / 代码审查）
2. 收集审查范围（哪些文件路径）
3. 构造 subagent prompt（只给路径 + 方法论，不给对话历史）
4. Spawn subagent
5. 收集报告 + 补充对话上下文
6. 呈现给用户
```

### Subagent 职责（执行）

```
1. 从零读所有指定文件
2. 按方法论逐维度审查
3. 产出结构化审查报告
4. 返回给主 agent
```

**关键**：subagent 的 prompt 只包含文件路径和审查方法论，不包含对话历史。这是独立性的保证。

## 模式一：文档审查（Doc Review）

> 触发时机：codegen 之前，或用户说"审查文档"

### 审查维度

```
① 文档完整性   每个文档的必要节都有内容吗？
② 跨文档一致   多个文档之间的定义对齐吗？
③ 约束声明     安全/性能/权限等约束在文档中声明了吗？
④ 可消费性     下游（codegen）能从文档生成代码吗？
```

### 第一维：文档完整性

每个文档是否包含必要的节，每节是否有实质内容。

| 文档 | 必要节 | 判定 |
|------|--------|------|
| contract.md | 共享约束 · 数据模型 · 错误码 · 领域索引 | 每节有实质内容（不是空节） |
| modules/*.md | 需求 · 验收条件 · 公共接口 · 数据模型 · 页面结构/依赖关系 | 每节有实质内容 |
| project.md | 技术栈 · 共享约束 | 每节有实质内容 |
| DESIGN.md | Token 系统（三层）· 字体 · 响应式 · 交互模式 · CSS 变量输出 | 每节有实质内容 |

**完整性扫描**：
```
1. 对每个文档：列出节标题
2. 对比必要节清单
3. 缺失节 → P1
4. 空节（只有标题没有内容）→ P1
```

### 第二维：跨文档一致

多个文档之间的定义是否对齐。

| 文档对 | 检查内容 | 判定 |
|--------|---------|------|
| contract.md ↔ modules/*.md | 模块划分和 contract 的领域索引一致 | 一一对应 |
| contract.md ↔ project.md | 共享约束一致（不矛盾） | 无冲突 |
| modules/*.md ↔ DESIGN.md | 组件引用了 DESIGN.md 中存在的 Token | Token 存在 |
| api/contract ↔ database/contract | 数据模型字段和类型一致 | 字段对齐 |
| api/contract ↔ frontend/contract | 端点定义和前端消费一致 | 接口对齐 |

### 第三维：约束声明

安全和非功能性约束在文档中声明了吗。

| 约束类型 | 应出现在 | 如果没写 |
|---------|---------|---------|
| 输入验证 | contract.md 共享约束 | P1 — 建议补充 |
| 认证授权 | contract.md 共享约束 | P1 — 明确哪些端点需要认证 |
| 数据量/容量 | project.md 共享约束 | P2 — 声明上限 |
| 错误处理策略 | contract.md | P1 — 声明错误码和响应格式 |
| 验证规则 | modules/*.md | P1 — 声明每个字段的校验时机 |

### 第四维：可消费性

codegen 能从这份文档生成代码吗？

| 检查项 | 判定 |
|--------|------|
| 每个端点有请求/响应定义（字段 + 类型） | 有 → 通过 |
| 数据模型有字段类型签名 | 有 → 通过 |
| 验收条件可测试（具体、可断言） | 可测试 → 通过 |
| 决策有编号（D1-D7）且有理由 | 有 → 通过 |
| 共享约束明确到可注入代码 | 可注入 → 通过 |

### 文档审查报告格式

```markdown
# 文档审查报告 — {Feature Name}

> 日期：{YYYY-MM-DD}
> 审查模式：文档审查（codegen 前）
> 审查者：独立 subagent（无对话上下文）

## 总览

| 维度 | 状态 | 问题数 |
|------|------|-------|
| 文档完整性 | ✅/❌ | {N} |
| 跨文档一致 | ✅/❌ | {N} |
| 约束声明 | ✅/❌ | {N} |
| 可消费性 | ✅/❌ | {N} |
| **总评** | **✅/❌** | **{N} 问题** |

## 问题清单

### [P0/P1/P2] {问题描述}
- **维度**：{完整性/一致性/约束/可消费}
- **文件**：{文件路径}
- **现状**：{缺少什么 / 不一致的地方}
- **修复建议**：{具体补充什么内容}

## 通过项 ✅
## 文档补全清单 📝
```

## 模式二：代码审查（Code Review）

> 触发时机：deploy 之前，或用户说"审查代码"

### 审查维度

```
① 投影一致     代码是文档的忠实投影吗？
② 约束声明     安全约束在文档中声明了吗？
③ 决策遵循     代码遵循 project.md 的决策吗？
④ 接口契约     跨领域文档互相引用一致吗？
```

### 第一维：投影一致（Projection Consistency）

代码是文档的忠实投影吗？——文档是源头，代码是投影，投影不能偏离源头。

| 文档来源 | 检查对象 | 对齐方式 |
|---------|---------|---------|
| contract.md 端点定义 | src/routes/ | 每个端点一一对应，无多余无遗漏 |
| contract.md 请求/响应 | 路由参数、返回值 | 参数名、类型、约束完全一致 |
| contract.md 错误码 | API 错误处理 | 错误码和 contract.md 定义一致 |
| modules/*.md 业务规则 | src/services/ | 每条规则有对应实现 |
| modules/*.md 验收条件 | 实现 + 测试 | 每个 AC 都有对应实现和测试 |
| 决策编号 (D1-D7) | 关键逻辑分支 | 关键分支有编号注释 |
| 共享约束 | 所有相关文件 | 多租户/权限/软删除等无遗漏 |

**投影扫描流程**：
```
1. 列出 contract.md 中所有端点
2. 列出 src/routes/ 中所有端点
3. 差集 = 投影缺失 + 幽灵代码
4. 幽灵代码 → 要么补文档，要么删代码
```

### 第二维：约束声明（Constraint Declaration）

安全约束在文档中声明了吗？先查文档声明，再查代码遵守。

| 步骤 | 做什么 | 判定 |
|------|--------|------|
| 1. 文档扫描 | contract.md 共享约束有安全条款吗？ | 有 → 步骤 2 · 没有 → 补文档 |
| 2. 代码对齐 | 代码遵守了文档声明的约束吗？ | 遵守 → 通过 · 不遵守 → 修代码 |
| 3. 盲区发现 | 代码里有安全措施但文档没声明？ | 有 → 补文档 + 记录决策 |

### 第三维：决策遵循（Decision Compliance）

代码遵循 project.md 的技术决策吗？

**决策漂移检测**：
```
1. 提取 package.json 中所有依赖
2. 提取 project.md 中声明的技术选型
3. 差集 = 决策漂移 → 更新 project.md 或移除依赖
```

### 第四维：接口契约（Interface Contract）

跨领域文档互相引用一致吗？

| 文档对 | 对齐方式 |
|--------|---------|
| api/contract ↔ frontend/contract | 端点、参数、类型一致 |
| api/contract ↔ database/contract | 数据模型、字段类型对齐 |
| 前端代码 ↔ api/contract | API 调用和文档一致 |
| contract 错误码 ↔ 前端错误处理 | 每个错误码有前端处理 |

### 代码审查报告格式

```markdown
# 代码审查报告 — {Feature Name}

> 日期：{YYYY-MM-DD}
> 审查模式：代码审查（deploy 前）
> 审查者：独立 subagent（无对话上下文）

## 总览

| 维度 | 状态 | 问题数 | 修代码 | 补文档 |
|------|------|-------|--------|--------|
| 投影一致 | ✅/❌ | {N} | {n} | {n} |
| 约束声明 | ✅/❌ | {N} | {n} | {n} |
| 决策遵循 | ✅/❌ | {N} | {n} | {n} |
| 接口契约 | ✅/❌ | {N} | {n} | {n} |
| **总评** | **✅/❌** | **{N} 问题** | **{n}** | **{n}** |

## 问题清单

### [P0/P1/P2] {问题描述}
- **维度**：{投影一致/约束声明/决策遵循/接口契约}
- **文件**：{文件路径:行号}
- **文档说了吗**：{是/否}
- **修复建议**：{修代码 / 补文档}

## 文档补全建议 📝
## 通过项 ✅
## 决策记录
## 豁免项
```

## 审查流程（主 Agent 编排）

### 1. 确定模式

```
用户说"审查文档" 或 codegen 即将开始 → 文档审查
用户说"审查代码" 或 deploy 即将开始  → 代码审查
不确定 → 问用户
```

### 2. 收集范围

```
文档审查范围：
  docs/ 下所有 .md 文件 + project.md + DESIGN.md

代码审查范围：
  docs/ + src/ + tests/
```

### 3. 构造 Subagent Prompt

subagent prompt 只包含：
- 审查模式（文档 or 代码）
- 文件路径列表
- 审查方法论（四维 + 检查表）
- 报告格式要求

**不包含**：对话历史、之前的决策、用户的偏好。这是独立性的保证。

### 4. Spawn Subagent

使用 Agent tool 创建独立 agent。agent 从零读所有文件，按方法论执行审查。

### 5. 收集 + 呈现

主 agent 收到 subagent 的报告后：
- 补充对话上下文中的信息（如有）
- 呈现给用户
- 引导下一步修复

### 6. 循环

```
审查不通过 → 分两路修复：
  补文档 → detail 补充 → 重新文档审查
  修代码 → codegen 重新生成 → 重新代码审查
直到所有 P0 项通过
```

## 入口/出口条件

**文档审查入口**：docs/ 下有完整文档结构（contract.md + modules/ + project.md）
**文档审查出口**：审查报告已生成 · 所有 P0/P1 项通过 · 用户确认

**代码审查入口**：src/ + tests/ 已生成 · 测试已通过 · 文档审查已通过（如有）
**代码审查出口**：审查报告已生成 · 所有 P0 项通过 · 文档补全建议已处理 · 用户确认

## 何时不使用

纯文档项目且不需要 codegen · 原型验证阶段 · 没有 contract.md 的代码

## 红旗清单

- 文档审查发现缺失节 → P1，补文档
- 跨文档定义不一致 → P1，对齐文档
- 幽灵代码（代码有文档没有）→ 补文档或删代码
- 安全约束未声明 → P0，先补文档
- 决策漂移（依赖未声明）→ P1，更新 project.md

## 验证清单

- [ ] 是否使用了 subagent（不是自审）？
- [ ] subagent prompt 是否只有路径 + 方法论（无对话历史）？
- [ ] 文档审查：四个维度都检查了？
- [ ] 代码审查：每个问题标注了"文档说了吗"？
- [ ] 修复建议区分了"修代码"和"补文档"？
- [ ] 审查报告有"文档补全建议"节？

## 历史维护（自动）

完成后追加 `docs/timeline.md`：`### {日期} — {feature} {文档/代码}审查 · {N} 问题（{P0数} P0 / {P1数} P1）`。超 100 行时归档。
