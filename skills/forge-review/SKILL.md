# Review — 审查阶段

## 职责

代码审查——从文档出发，验证代码是文档的忠实投影，发现文档的盲区并驱动补全。

**核心洞察**：传统 code review 问"代码有什么问题"。Forge 问"文档漏了什么？代码偏离了文档吗？"——测试验证功能正确性，但测试不验证文档对齐。测试通过 ≠ 代码合格，因为代码可能偏离了 contract 但碰巧能跑，或者引入了文档未声明的约束。

**方法论**：投影一致 → 约束声明 → 决策遵循 → 接口契约。

**第一原则**：发现任何问题，先问"文档里写了吗？"
- 写了但代码没遵守 → 修代码
- 没写但代码里存在 → 补文档 + 记录决策 + 评估代码是否需要调整
- 没写且代码也没有 → 补文档（声明约束）

## 与上下游的边界

**上游**：读 src/ + tests/（代码和测试）+ contract.md + modules/*.md（文档）+ project.md（技术决策）+ DESIGN.md（设计系统）
**下游**：审查报告交给 codegen（修代码）或 detail（补文档）

**和 forge-codegen 的切法**：codegen 从文档生成代码，review 从文档审查代码——同一个合约的两面
**和 forge-fe-accept 的切法**：fe-accept 做前端视觉/质量验收（Token、响应式、可访问性），review 做跨领域文档对齐审查
**和 forge-test-strategy 的切法**：test-strategy 定义测试策略，review 审查测试是否覆盖了文档中的验收条件
**和 forge-deploy 的切法**：review 通过 = deploy 的前置条件

## 核心方法论：四维文档驱动审查

```
① 投影一致     代码是文档的忠实投影吗？
② 约束声明     安全约束在文档中声明了吗？
③ 决策遵循     代码遵循 project.md 的决策吗？
④ 接口契约     跨领域文档互相引用一致吗？
```

**审查不修改代码。** review 只判定 + 给修复建议。代码修复是 codegen 的事，文档补全是 detail 的事。

### 第一维：投影一致（Projection Consistency）

代码是文档的忠实投影吗？——这是 Forge 审查的核心。文档是源头，代码是投影，投影不能偏离源头。

**检查路径**：从文档出发，检查代码是否对齐。

| 文档来源 | 检查对象 | 对齐方式 |
|---------|---------|---------|
| contract.md 端点定义 | src/routes/ | 每个端点一一对应，无多余无遗漏 |
| contract.md 请求/响应 | 路由参数、返回值 | 参数名、类型、约束完全一致 |
| contract.md 错误码 | API 错误处理 | 错误码和 contract.md 定义一致 |
| modules/*.md 业务规则 | src/services/ | 每条规则有对应实现 |
| modules/*.md 验收条件 | 实现 + 测试 | 每个 AC 都有对应实现和测试 |
| 决策编号 (D1-D7 / AC1-AC8) | 关键逻辑分支 | 关键分支有编号注释 |
| 共享约束 | 所有相关文件 | 多租户/权限/软删除等无遗漏 |

**投影扫描流程**：
```
1. 列出 contract.md 中所有端点
2. 列出 src/routes/ 中所有端点
3. 差集 = 文档有但代码没有（投影缺失）+ 代码有但文档没有（幽灵代码）
4. 对每个交集端点：比对参数、返回值、错误码
5. 幽灵代码 → 要么补文档，要么删代码
```

**核心判断**：代码里存在但文档里没有的东西 = 幽灵代码。它要么是文档遗漏（补文档），要么是过度实现（删代码）。不能放过。

### 第二维：约束声明（Constraint Declaration）

安全约束在文档中声明了吗？——传统审查直接检查代码安全。Forge 先检查文档有没有声明安全约束，再检查代码有没有遵守。

**检查路径**：先查文档声明，再查代码遵守。

| 步骤 | 做什么 | 判定 |
|------|--------|------|
| 1. 文档扫描 | contract.md 共享约束有安全条款吗？ | 有 → 步骤 2 · 没有 → 补文档 |
| 2. 代码对齐 | 代码遵守了文档声明的约束吗？ | 遵守 → 通过 · 不遵守 → 修代码 |
| 3. 盲区发现 | 代码里有安全措施但文档没声明？ | 有 → 补文档 + 记录决策 |

**常见安全约束（文档应声明的）**：

| 约束类型 | 文档中应该出现在 | 如果文档没写 |
|---------|----------------|-------------|
| 输入验证 | contract.md 共享约束 | 建议补充 — 列出需要验证的端点 |
| 认证授权 | contract.md 共享约束 | 建议补充 — 明确哪些端点需要认证 |
| 数据脱敏 | contract.md 响应定义 | 建议补充 — 标注敏感字段 |
| 密钥管理 | project.md 技术决策 | 建议补充 — 声明密钥存储方式 |
| CORS/CSP | project.md 技术决策 | 建议补充 — 声明安全策略 |
| 速率限制 | contract.md 共享约束 | 建议补充 — 声明限流策略 |

**和传统安全审查的区别**：
```
传统：扫描代码 → 发现 SQL 注入风险 → 修代码
Forge：扫描文档 → 没有输入验证约束 → 补文档声明 → 再检查代码是否遵守
```

文档补全是根因修复——不补文档，下次 codegen 还会生成同样的漏洞。

### 第三维：决策遵循（Decision Compliance）

代码遵循 project.md 的技术决策吗？引入了新依赖但没更新文档 = 决策漂移。

**检查路径**：从 project.md 出发，检查代码是否遵循。

| 文档来源 | 检查对象 | 对齐方式 |
|---------|---------|---------|
| project.md 技术选型 | package.json / imports | 使用了选定的框架/库 |
| project.md 目录结构 | src/ 实际结构 | 文件在正确位置 |
| project.md 共享约束 | 所有代码 | 约束在所有相关文件中遵守 |

**决策漂移检测**：
```
1. 提取 package.json 中所有依赖
2. 提取 project.md 中声明的技术选型
3. 差集 = 代码引入了文档没声明的依赖 → 决策漂移
4. 每个漂移项：
   - 确实需要 → 更新 project.md + 记录决策（为什么引入、替代方案是什么）
   - 不需要 → 移除依赖
```

**分层纪律**（从 project.md 推导）：
```
routes/   → 只处理 HTTP（解析请求、调用 service、返回响应）
services/ → 只处理业务逻辑（不关心 HTTP 状态码）
schemas/  → 只定义数据结构和验证规则
db/       → 只处理数据库操作
```

跨层调用 = 架构决策偏离 → 要么修代码，要么更新 project.md 记录新的架构决策。

### 第四维：接口契约（Interface Contract）

跨领域文档互相引用一致吗？——如果 api/contract.md 和 frontend/contract.md 定义不一致，生成出来的代码必然不对齐。

**检查路径**：从文档间的引用关系出发。

| 文档对 | 检查对象 | 对齐方式 |
|--------|---------|---------|
| api/contract.md ↔ frontend/contract.md | 端点、参数、类型 | 前端引用的 API 定义和 API 文档一致 |
| api/contract.md ↔ database/contract.md | 数据模型、字段类型 | API 模型和数据库表结构对齐 |
| 前端代码 ↔ api/contract.md | API 调用 | 前端调用的端点、参数、类型和文档一致 |
| contract.md 错误码 ↔ 前端错误处理 | 错误处理链 | 每个错误码有对应的前端处理 |

**契约对齐流程**：
```
1. 提取 api/contract.md 的所有端点定义
2. 提取前端代码中所有 API 调用
3. 逐个比对：端点路径、HTTP 方法、参数、返回值
4. 不一致 → 先确认哪边是源头（通常是 API contract）
5. 源头文档有误 → 修文档 + 重新生成代码
6. 投影有误 → 修代码
```

## AI 的角色

| 阶段 | AI 角色 | 行为 |
|------|---------|------|
| 投影一致 | 投影校验者 | 逐条比对文档和代码，找分歧和幽灵代码 |
| 约束声明 | 文档完整性评估者 | 检查文档是否声明了应有的约束，再检查代码遵守 |
| 决策遵循 | 决策漂移检测者 | 检查代码是否偏离 project.md 的技术决策 |
| 接口契约 | 契约对齐校验者 | 检查跨领域文档间的引用一致性 |
| 报告 | 文档驱动修复建议者 | 产出审查报告，区分"修代码"和"补文档" |

## 审查报告格式

```markdown
# 审查报告 — {Feature Name}

> 日期：{YYYY-MM-DD}
> 审查人：{AI + 用户确认}

## 总览

| 维度 | 状态 | 问题数 | 修代码 | 补文档 |
|------|------|-------|--------|--------|
| 投影一致 | ✅/❌ | {N} | {n} | {n} |
| 约束声明 | ✅/❌ | {N} | {n} | {n} |
| 决策遵循 | ✅/❌ | {N} | {n} | {n} |
| 接口契约 | ✅/❌ | {N} | {n} | {n} |
| **总评** | **✅/❌** | **{N} 问题** | **{n}** | **{n}** |

## 问题清单

### [P0] {问题描述}
- **维度**：{投影一致/约束声明/决策遵循/接口契约}
- **文件**：{文件路径:行号}
- **文档说了吗**：{是/否}
  - 是 → {引用文档段落}，代码偏离 → **修代码**
  - 否 → 文档盲区 → **补文档** + {建议声明内容}
- **现状**：{实际代码}
- **修复建议**：{具体怎么改，指向文档还是代码}

### [P1] {问题描述}
...

## 文档补全建议 📝

> 以下问题根因是文档不完整，建议先补文档再修代码。

- [ ] {文档路径} — {建议补充内容} — {原因}

## 通过项 ✅

- [维度] {检查项} — {通过理由}

## 决策记录

- D{n}: {审查标准决策} — {理由}

## 豁免项

- {检查项} — {豁免理由}
```

**和传统审查报告的区别**：每个问题都标注"文档说了吗"，修复建议区分"修代码"和"补文档"。新增"文档补全建议"节，集中列出需要补全的文档。

## 审查流程

### 准备阶段

```
1. 确认审查范围：哪些模块/端点？
2. 读上游文档：contract.md + modules/*.md + project.md + DESIGN.md
3. 读代码：src/ + tests/
4. 确认 fe-accept 已通过（如有前端）
5. 确认测试已通过
```

### 执行阶段

```
按四个维度依次审查：
  投影一致 → 约束声明 → 决策遵循 → 接口契约

每个维度：
  1. 从文档出发（不是从代码出发）
  2. 逐项检查 → 记录 pass/fail
  3. 不合格项标注"文档说了吗"
  4. 给出修复方向：修代码 / 补文档 / 两者都要
```

### 报告阶段

```
1. 汇总四个维度的结果
2. 生成总评（全部通过 = ✅，任一 P0 = ❌）
3. 区分"修代码"和"补文档"问题
4. 记录决策和豁免
```

### 循环阶段

```
审查不通过 → 分两路修复：
  修代码 → codegen 重新生成
  补文档 → detail 补充文档 → 再审查
直到所有 P0 项通过
```

## 交接检查点（审查前）

审查前必须确认前置条件满足。**前置条件不满足 = 审查结果不可信。**

```
前置条件检查：

□ 测试已通过（所有测试 green）
□ fe-accept 已通过（如有前端，验收报告 ✅）
□ contract.md + modules/*.md 完整
□ project.md 技术决策完整
□ src/ + tests/ 已生成

缺失项处理：
- 测试未通过 → 中止审查，先修测试
- fe-accept 未通过 → 中止审查，先修前端
- 文档不完整 → 中止审查，先补文档
- 代码未生成 → 中止审查，先跑 codegen
```

## 入口/出口条件

**入口**：src/ + tests/ 已生成 · 测试已通过 · fe-accept 已通过（如有前端）· contract.md + modules/*.md 完整
**出口**：审查报告已生成 · 所有 P0 项通过（或用户确认豁免）· 文档补全建议已处理 · 用户确认

## 何时不使用

纯文档项目 · 没有 contract.md 的代码 · 原型验证阶段（不需要严格审查）

## 红旗清单

- 幽灵代码（代码里有，文档里没有）→ 补文档或删代码，不能放过
- 文档声明了约束但代码没遵守 → P0，修代码
- 安全约束文档未声明 → P0，先补文档再检查代码
- 引入未声明的依赖 → P1，更新 project.md 记录决策或移除
- 跨层调用 → P1，修代码或更新 project.md 记录架构变更
- 跨领域文档不一致 → P1，先对齐文档再修代码
- 关键逻辑没有决策编号注释 → P2，标注
- 测试未通过就开始审查 → 中止，先修测试

## 验证清单

- [ ] 四个维度是否都从文档出发审查？
- [ ] 每个问题是否标注了"文档说了吗"？
- [ ] 修复建议是否区分了"修代码"和"补文档"？
- [ ] contract.md 的每个端点是否都有对应代码？
- [ ] 代码里是否有文档未声明的东西（幽灵代码）？
- [ ] 安全约束是否在文档中声明？
- [ ] 是否引入了未声明的依赖？
- [ ] 跨领域文档是否互相引用一致？
- [ ] 审查报告是否有"文档补全建议"节？
- [ ] 豁免项是否有理由？
