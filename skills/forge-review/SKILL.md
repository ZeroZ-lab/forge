# Review — 审查阶段

## 职责

代码审查——验证代码和文档对齐、安全合规、架构一致、集成完整。

**核心洞察**：测试验证功能正确性，审查验证代码质量。测试通过 ≠ 代码合格——测试不检查文档对齐（代码偏离了 contract 但功能碰巧对）、不检查架构一致性（引入了未声明的依赖但能跑）、不检查集成完整性（前后端类型不一致但运行时没报错）。

**方法论**：文档对齐 → 安全 → 架构 → 集成。

## 与上下游的边界

**上游**：读 src/ + tests/（代码和测试）+ contract.md + modules/*.md（文档）+ project.md（技术决策）+ DESIGN.md（设计系统）+ testing/test-cases.md（测试策略）
**下游**：审查报告交给 codegen（修复）或 deploy（发布）

**和 forge-codegen 的切法**：codegen 生成代码，review 审查代码和文档是否对齐
**和 forge-fe-accept 的切法**：fe-accept 做前端视觉/质量验收（Token、响应式、可访问性），review 做跨领域代码级审查
**和 forge-test-strategy 的切法**：test-strategy 定义测试策略，review 审查测试是否覆盖了策略
**和 forge-deploy 的切法**：review 通过 = deploy 的前置条件

## 核心方法论：四维审查

```
① 文档对齐     代码是否忠实于 contract.md + modules/*.md？
② 安全审查     有没有常见安全漏洞？共享约束是否遵守？
③ 架构一致     代码是否遵循 project.md 的技术决策？
④ 集成完整     跨领域接口是否对齐？
```

**审查不修改代码。** review 只判定 + 给修复建议，修复是 codegen 的事。

### 第一维：文档对齐（Doc-Code Alignment）

逐模块检查代码和文档是否一致。这是 Forge 审查的核心——文档是源代码，代码是投影，投影不能偏离源头。

| 检查项 | 判定方式 | 通过标准 |
|--------|---------|---------|
| API 端点 | src/routes/ 和 api/contract.md 逐条比对 | 每个端点一一对应，无多余无遗漏 |
| 请求/响应 | 参数名、类型、约束和 contract.md 对齐 | 完全一致 |
| 错误码 | API 返回的错误码和 contract.md 定义一致 | 完全一致 |
| 业务规则 | src/services/ 逻辑和 modules/*.md 业务规则对齐 | 每条规则有对应实现 |
| 验收条件 | 每个 AC 都有对应的实现和测试 | AC 全覆盖 |
| 决策编号 | 关键逻辑分支有注释引用 D1-D7 / AC1-AC8 | 关键分支有编号 |
| 共享约束 | 多租户/权限/软删除等在所有相关文件中遵守 | 无遗漏 |

**文档对齐扫描**：
```
1. 列出 contract.md 中所有端点
2. 列出 src/routes/ 中所有端点
3. 差集 = 文档有但代码没有 + 代码有但文档没有
4. 对每个交集端点：比对参数、返回值、错误码
```

### 第二维：安全审查（Security）

按风险等级检查常见安全漏洞。

| 检查项 | 常见风险 | 严重级别 |
|--------|---------|---------|
| 输入验证 | SQL 注入、XSS、路径遍历、命令注入 | P0 |
| 认证授权 | JWT 未验证、权限未检查、越权访问 | P0 |
| 数据暴露 | 敏感字段返回前端、日志中打印密码、错误信息暴露内部路径 | P0 |
| 密钥管理 | 硬编码密钥、明文密码、未加密的 token | P0 |
| CORS/CSP | 配置过宽（`*`）| P1 |
| 依赖安全 | 已知漏洞的依赖包版本 | P1 |
| 速率限制 | 无 rate limiting 的公开端点 | P1 |
| 文件上传 | 无类型校验、无大小限制、无病毒扫描 | P1 |

**安全审查规则**：
- P0 安全问题 = 阻断发布，必须修复
- P1 安全问题 = 应修复，可延期但需记录
- 安全问题的修复建议必须具体到代码行

### 第三维：架构一致（Architecture Consistency）

检查代码是否遵循 project.md 和 contract.md 的技术决策。

| 检查项 | 判定方式 | 通过标准 |
|--------|---------|---------|
| 技术选型 | 代码使用了 project.md 选定的框架/库 | 无未声明的依赖 |
| 目录结构 | src/ 结构和 project.md 定义一致 | 文件在正确位置 |
| 分层纪律 | 路由不管业务逻辑，服务不管 HTTP | 无跨层调用 |
| 状态管理 | 前端状态归属符合 frontend/contract.md 的 F2 | 状态在正确层级 |
| 样式方案 | 前端样式符合 frontend/contract.md 的 F3 | 使用选定方案 |
| 数据请求 | 前端请求方式符合 frontend/contract.md 的 F4 | 使用选定方案 |
| 表单方案 | 前端表单符合 frontend/contract.md 的 F5 | 使用选定方案 |

**分层纪律规则**：
```
routes/   → 只处理 HTTP（解析请求、调用 service、返回响应）
services/ → 只处理业务逻辑（不关心 HTTP 状态码）
schemas/  → 只定义数据结构和验证规则
db/       → 只处理数据库操作
```

### 第四维：集成完整（Integration Integrity）

检查跨领域接口是否对齐。

| 检查项 | 判定方式 | 通过标准 |
|--------|---------|---------|
| API ↔ 前端 | 前端调用的端点、参数、类型和 api/contract.md 一致 | 完全对齐 |
| API ↔ 数据库 | API 数据模型和 database/contract.md 表结构一致 | 字段和类型对齐 |
| 前端 ↔ 设计 | fe-accept 已通过（确认 Token 合规） | fe-accept 报告通过 |
| 错误处理链 | API 错误码 → 前端错误处理 → 用户反馈，链路完整 | 每个错误码有前端处理 |
| 类型一致 | 前端类型定义和 API schema 对齐 | 类型匹配或从 schema 生成 |

**集成审查流程**：
```
1. 提取 api/contract.md 的所有端点定义
2. 提取前端代码中所有 API 调用
3. 逐个比对：端点路径、HTTP 方法、参数、返回值
4. 提取 api/contract.md 的错误码
5. 检查前端是否有对应的错误处理
```

## AI 的角色

| 阶段 | AI 角色 | 行为 |
|------|---------|------|
| 文档对齐 | 一致性检查者 | 逐条比对代码和文档，找分歧 |
| 安全 | 安全审计者 | 按风险清单扫描常见漏洞 |
| 架构 | 架构守护者 | 检查代码是否偏离技术决策 |
| 集成 | 集成验证者 | 检查跨领域接口是否对齐 |
| 报告 | 判定记录者 | 产出审查报告 + 修复建议 |

## 审查流程

### 准备阶段

```
1. 确认审查范围：哪些模块/端点？
2. 读上游文档：contract.md + modules/*.md + project.md + DESIGN.md
3. 读代码：src/ + tests/
4. 确认 fe-accept 已通过（如有前端）
5. 确认测试已通过
```

### 执行阶段

```
按四个维度依次审查：
  文档对齐 → 安全 → 架构 → 集成
每个维度：逐项检查 → 记录 pass/fail → 不合格项写修复建议 + 优先级
```

### 报告阶段

```
1. 汇总四个维度的结果
2. 生成总评（全部通过 = ✅，任一 P0 = ❌）
3. 记录决策（为什么这个标准是这个级别）
4. 记录豁免（为什么不审查某项）
```

### 循环阶段

```
审查不通过 → 修复建议交给 codegen → 重新生成 → 重新审查
直到所有 P0 项通过
```

## 交接检查点（审查前）

审查前必须确认前置条件满足。**前置条件不满足 = 审查结果不可信。**

```
前置条件检查：

□ 测试已通过（所有测试 green）
□ fe-accept 已通过（如有前端，验收报告 ✅）
□ contract.md + modules/*.md 完整
□ project.md 技术决策完整
□ src/ + tests/ 已生成

缺失项处理：
- 测试未通过 → 中止审查，先修测试
- fe-accept 未通过 → 中止审查，先修前端
- 文档不完整 → 中止审查，先补文档
- 代码未生成 → 中止审查，先跑 codegen
```

## 入口/出口条件

**入口**：src/ + tests/ 已生成 · 测试已通过 · fe-accept 已通过（如有前端）· contract.md + modules/*.md 完整
**出口**：审查报告已生成 · 所有 P0 项通过（或用户确认豁免）· 用户确认

## 何时不使用

纯文档项目 · 没有 contract.md 的代码 · 原型验证阶段（不需要严格审查）

## 红旗清单

- 代码和 contract.md 端点不一致 → P0，强制对齐
- 安全问题（SQL 注入、XSS、硬编码密钥）→ P0，强制修复
- 引入未声明的依赖 → P1，强制记录到 project.md 或移除
- 跨层调用（路由直接查数据库）→ P1，强制重构
- 关键逻辑没有决策编号注释 → P2，强制标注
- 前后端类型不一致 → P1，强制对齐
- 错误码没有前端处理 → P1，强制补充
- 测试未通过就开始审查 → 中止，先修测试

## 验证清单

- [ ] 四个维度是否都审查了？
- [ ] contract.md 的每个端点是否都有对应代码？
- [ ] 是否有 P0 安全问题未修复？
- [ ] 是否引入了未声明的依赖？
- [ ] 分层纪律是否遵守？
- [ ] 前后端接口是否对齐？
- [ ] 每个错误码是否有前端处理？
- [ ] 审查报告是否有修复建议（具体到文件和行号）？
- [ ] 豁免项是否有理由？
