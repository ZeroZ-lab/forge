# Test Strategy — 决策协议

## 职责

引导人类完成测试策略的 5 个决策点。

**原则**：Skill 只问业务问题。技术问题模型自己搜索、自己评估。

每个决策点：
1. 问业务问题（只有人类能回答的）
2. 根据回答，搜索最新技术方案，生成 2-3 个选项 + 各自代价
3. 给出推荐 + 理由
4. 等人类确认
5. 记录选择 + 理由 + 被拒方案

## 产出结构

```
docs/features/<feature>/testing/
├── contract.md      # T1-T5 决策 + 覆盖矩阵 + 测试规范（~80 行）
└── changelog.md
```

---

## 方法论：测试金字塔

测试策略的核心方法论：

1. **分层测试** — 底层多且快（单元），顶层少且慢（E2E）
2. **隔离性** — 测试之间不互相依赖，可以任意顺序运行
3. **可重复** — 同一个测试跑 100 次结果一样

每个决策点都是这套方法论的一个切面。

## 决策点

### T1: 测试类型

**问人类：**
- 大概有多少个 API 端点？
- 出问题时需要多快定位到根因？
- 有 QA 团队还是开发者自己写测试？
- 这个项目出 bug 的代价有多大？（丢钱 vs 显示错一个数字）

**不变原则：**
- 测试类型由**风险等级 + 定位速度需求**决定
- 测试金字塔：底层多且快，顶层少且慢
- 没有测试的代码 = 不存在的功能

**记录**：测试类型组合 + 各类型占比 + 选择理由 + 被拒方案

---

### T2: 覆盖策略

**问人类：**
- 端点数量多吗？
- 所有功能同等重要，还是有明显的核心流程？
- 团队愿意在测试上花多少时间？

**不变原则：**
- 关键路径必须全覆盖（支付、认证、数据写入）
- 覆盖率和维护成本是正相关的
- 100% 覆盖率是虚荣指标，有效覆盖才是目标

**记录**：策略 + 选择理由 + 被拒方案

---

### T3: 测试数据

**问人类：**
- 数据模型复杂吗？（多表关联 / 嵌套结构）
- 测试数据需要看起来真实吗？
- 测试之间需要完全隔离还是可以共享基础数据？

**不变原则：**
- 测试数据必须可重复生成
- 测试之间不能互相依赖（A 测试的输出不能是 B 测试的输入）
- 数据越真实，越能发现真实场景的 bug

**记录**：策略 + 数据生成方式 + 选择理由 + 被拒方案

---

### T4: Mock 策略

**问人类：**
- CI 环境能跑 Docker 吗？
- 有多少个外部依赖？（第三方 API、消息队列、缓存）
- 测试跑多久可以接受？

**不变原则：**
- 真实依赖 > Mock（能发现集成问题）
- 外部服务必须 Mock（不可控、不稳定、有费用）
- 速度太慢的测试不会被运行 = 不存在的测试

**记录**：策略 + 真实/Mock 清单 + 选择理由 + 被拒方案

---

### T5: CI 集成

**问人类：**
- 测试跑完大概要多久？
- 发布频率是多少？（每次提交 / 每天 / 每周）
- 测试失败了怎么办？（阻断发布 / 告警但不阻断）

**不变原则：**
- 测试必须在 CI 中跑，本地跑的测试约等于没跑
- 测试时间 > 10 分钟必须优化，否则开发者会跳过
- 失败的测试必须阻断发布（否则测试失去意义）

**记录**：策略 + 超时设置 + 失败策略 + 选择理由 + 被拒方案

---

## 文档约束

产出必须包含：
1. **T1-T5 决策**：每个选择 + 理由 + 被拒方案
2. **测试框架表**
3. **覆盖矩阵**：每个端点的覆盖情况
4. **测试规范**：命名、隔离、环境要求

---

## 恒久约定

### 文件命名
- 合约测试：`<module>.contract.test.{ext}`
- 单元测试：`<module>.unit.test.{ext}`
- E2E 测试：`<flow>.e2e.test.{ext}`

### 测试结构
- describe 按端点/模块分组
- 每个 test case 验证一个行为
- 测试名 = 行为描述 + 预期结果

### 测试隔离
- 每个测试文件独立 setup/teardown
- 测试间不共享可变状态
- 不依赖执行顺序
