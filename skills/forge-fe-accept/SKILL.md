# FE Accept — 前端质量验收

## 职责

定义前端产物"什么算通过"——四维判定，产出验收报告。

**核心洞察**：前端验收不是跑测试工具——测试工具是下游消费者。fe-accept 的职责是**定义验收标准和判定方式**，让测试结果可追溯到设计决策。"测试通过但用户觉得丑"说明验收标准缺了视觉维度。

**和测试框架的区别**：
```
测试框架（Jest/Playwright）：执行测试，报告 pass/fail
fe-accept：定义测什么、什么算 pass、怎么追溯决策
```

## 与上下游的边界

**上游**：读 frontend/modules/*.md（验收条件）+ DESIGN.md（设计标准）+ src/（实际代码）+ 可运行的页面
**下游**：验收报告交给 fe-artifact（修复）或 deploy（发布）

**和 forge-fe-artifact 的切法**：
- fe-artifact 生成代码
- fe-accept 判定代码是否合格，不合格时给出修复建议（不修改代码）

**和 forge-test-strategy 的切法**：
- test-strategy 定义**怎么测**（测试类型、覆盖策略、Mock、CI）
- fe-accept 定义**前端特有的验收维度**（视觉、响应式、Token 合规、性能边界）

**和 forge-test-cases 的切法**：
- test-cases 推导具体测试场景
- fe-accept 定义每个维度的通过标准和判定方式

## 核心方法论：四维验收

```
① 功能正确     组件行为符合 modules/*.md 的验收条件
② 视觉一致     产物符合 DESIGN.md 的 Token 和模式
③ 适应性       响应式断点、暗色模式、可访问性
④ 性能边界     数据量、渲染量、交互频率的极限在哪
```

**信息只往下流。** fe-accept 不修改 DESIGN.md，不修改组件代码——它只判定，修复是 fe-artifact 的事。

### 第一维：功能正确

**读什么**：frontend/modules/{name}.md 的"验收条件"（AC1-ACn）

**判定什么**：

| 检查项 | 判定方式 | 通过标准 |
|--------|---------|---------|
| 验收条件覆盖 | 逐条核对 AC | 每条 AC 都有对应的实现和测试 |
| 五状态实现 | 检查代码 | idle/loading/error/empty/success 都有 |
| 交互行为 | 手动测试 / E2E | 点击、输入、拖拽等行为符合规格 |
| 数据正确性 | 和 api/contract.md 对齐 | 请求参数、返回值、错误码一致 |
| 边界条件 | 检查 modules 边界 | 空数据、超长文本、极端数值都有处理 |

### 第二维：视觉一致

**读什么**：DESIGN.md 的三层 Token + 交互模式库

**判定什么**：

| 检查项 | 判定方式 | 通过标准 |
|--------|---------|---------|
| Token 合规 | 代码扫描 | 无硬编码设计值（`#3B82F6`），只用 Token |
| 间距一致 | 视觉对比 | 元素间距符合 DESIGN.md 的 space token |
| 色彩正确 | 代码扫描 + 视觉 | 使用了正确的语义/组件 Token |
| 字体层级 | 视觉对比 | 标题/正文/辅助文本使用正确的 font token |
| 组件状态 | 视觉检查 | hover/focus/disabled/loading 状态样式正确 |
| 模式一致 | 交互对比 | 使用了 DESIGN.md 定义的交互模式 |
| 反 AI 味 | 和默认值对比 | 和 Material/Ant 默认值不雷同 |

**Token 合规扫描规则**：
```
❌ color: #3B82F6
✅ color: var(--color-accent)

❌ padding: 16px
✅ padding: var(--space-md)

❌ font-size: 14px
✅ font-size: var(--font-small-size)

❌ border-radius: 8px
✅ border-radius: var(--radius-md)
```

**自动化扫描（推荐）**：
手动扫描在大型项目不可行。fe-accept 应优先使用自动化工具：

```bash
# 扫描 CSS 文件中的硬编码色值（排除 CSS 变量定义行）
grep -rn "color:.*#[0-9a-fA-F]\{3,6\}" src/**/*.css | grep -v "^\s*--"

# 扫描硬编码像素值（排除 0px 和 1px 边框）
grep -rn "padding:\|margin:\|font-size:\|width:\|height:" src/**/*.css | grep -E "[2-9][0-9]*px|1[0-9]+px"

# 统计 Token 使用率
grep -c "var(--" src/**/*.css | awk -F: '{sum+=$2} END {print "Token 引用总数:", sum}'
```

**扫描结果解读**：
- 硬编码色值 > 0 → P0（必须修复，破坏主题切换）
- 硬编码像素值（非 0/1px）> 5 处 → P1（应修复，间距不一致）
- Token 引用总数 < 组件数 × 10 → P2（Token 抽象不够，很多组件直接写样式）

**允许的硬编码例外**：
- `0px` / `1px`（边框宽度，无 Token 必要）
- `100%` / `auto`（布局值，非设计值）
- 第三方组件库内部样式（不可控）
- 每个例外必须在代码旁注释说明理由

### 第三维：适应性

**判定什么**：

| 检查项 | 判定方式 | 通过标准 |
|--------|---------|---------|
| 响应式断点 | 多视口截图（375/768/1024/1440） | 每个断点布局合理，无溢出/截断 |
| Mobile-first | 代码审查 | 基础样式是移动端，min-width 增强桌面端 |
| 触控目标 | 测量 | 交互元素 ≥ 44×44pt |
| 暗色模式 | 切换检查（如 DESIGN.md 定义） | 所有元素可读，对比度 ≥ 4.5:1 |
| Keyboard nav | Tab 遍历 | 所有交互元素可通过键盘访问 |
| ARIA 正确 | axe-core 扫描 | 无 critical/serious 违规 |
| Focus 管理 | Tab 遍历 | dialog 有 focus trap，关闭时回到触发元素 |
| 色彩非唯一载体 | 视觉检查 | 错误状态有图标/文字，不只靠颜色 |

### 第四维：性能边界

**读什么**：frontend/contract.md 的共享约束（性能要求）

**判定什么**：

| 检查项 | 判定方式 | 通过标准 |
|--------|---------|---------|
| 首屏渲染 | Lighthouse | LCP ≤ 2.5s（按 project.md 约束调整） |
| 交互响应 | INP 测量 | INP ≤ 200ms |
| 包体积 | 构建分析 | 首屏 JS ≤ {project.md 定义} KB |
| 大列表帧率 | 帧率测量 | ≥ 55fps（数据量按 contract.md 约束） |
| 图片优化 | 检查 | WebP/AVIF + lazy loading + 适当尺寸 |
| 无阻塞资源 | 检查 | 关键 CSS 内联 / 字体预加载 |

**边界值从哪来**：
- project.md 定义了 → 用 project.md 的值
- project.md 没定义 → 用行业基准（LCP 2.5s / INP 200ms / CLS 0.1）
- 行业基准不适用 → fe-accept 定义 + 记录理由

## AI 的角色

| 阶段 | AI 角色 | 行为 |
|------|---------|------|
| 功能 | 验收条件审查者 | 逐条核对 AC，确认每条有实现和测试 |
| 视觉 | Token 合规检查者 | 扫描代码中的硬编码值，对比 DESIGN.md |
| 适应 | 多环境测试者 | 多视口截图 + 键盘遍历 + 暗色切换 |
| 性能 | 边界定义者 | 从 contract 推导性能边界，测量是否达标 |
| 报告 | 判定记录者 | 产出 pass/fail + 修复建议 + 决策记录 |

## 验收报告格式

```markdown
# 验收报告 — {Feature/Component Name}

> 日期：{YYYY-MM-DD}
> 验收人：{AI + 用户确认}

## 总览

| 维度 | 状态 | 通过/总项 |
|------|------|----------|
| 功能正确 | ✅/❌ | {N}/{M} |
| 视觉一致 | ✅/❌ | {N}/{M} |
| 适应性 | ✅/❌ | {N}/{M} |
| 性能边界 | ✅/❌ | {N}/{M} |
| **总评** | **✅/❌** | **{N}/{M}** |

## 通过项 ✅

- [维度] {检查项} — {通过理由}

## 未通过项 ❌

### {检查项}
- **维度**：{功能/视觉/适应/性能}
- **现状**：{实际表现}
- **标准**：{应该是什么}
- **修复建议**：{怎么改，具体到文件和代码}
- **优先级**：P0（阻断发布）/ P1（应修复）/ P2（可延后）

## 决策记录

- D{n}: {验收标准决策} — {理由}
  例：D1: 大列表帧率标准定为 55fps 而非 60fps — 低端设备 60fps 不现实，
      55fps 用户感知不到卡顿（参考：Chrome UX Report p75）

## 豁免项

> 明确记录哪些维度不验收，以及为什么。

- {维度/检查项} — {豁免理由}
  例：暗色模式 — project.md 明确当前版本只做亮色
```

## 验收流程

### 准备阶段

```
1. 确认验收范围：哪些组件/页面？
2. 读上游文档：modules/*.md + DESIGN.md + contract.md
3. 交接检查点：验证上游文档完整性（见下）
4. 确定每个维度的通过标准（用默认值 or 自定义）
5. 确认豁免项（哪些维度不适用）
```

### 交接检查点（读取后、验收前）

验收前必须确认上游文档完整。**不完整的上游文档 = 验收标准缺失 = 验收结果不可信。**

```
上游文档完整性检查：

DESIGN.md 检查：
□ 三层 Token 都有（原始值 / 语义层 / 组件层）
□ Token 统计摘要已输出（fe-system 出口必输出）
□ CSS 变量输出段存在
□ 交互模式库覆盖待验收组件类型
□ 响应式断点已定义

modules/*.md 检查：
□ 每个组件有验收条件（AC1-ACn）
□ 验收条件可枚举、可测试（不是"用户体验好"）

缺失项处理：
- DESIGN.md 缺 Token 统计 → 中止验收，提示先补完 fe-system
- DESIGN.md 缺交互模式 → 对应维度降级为"最佳实践"标准，不引用 DESIGN.md
- modules 缺验收条件 → 对应组件跳过功能正确维度，标注"无可验收条件"
- 多处缺失 → 中止验收，提示用户先跑上游 Skill
```

**为什么需要交接检查点**：测试发现，当 DESIGN.md 缺少 Token 统计时，fe-accept 不知道有多少 Token 需要验收，导致验收覆盖率不清。在验收前拦截 = 避免无效验收。

### 执行阶段

```
按四个维度依次判定：
  功能 → 视觉 → 适应 → 性能
每个维度：逐项检查 → 记录 pass/fail → 不合格项写修复建议
```

### 报告阶段

```
1. 汇总四个维度的结果
2. 生成总评（全部通过 = ✅，任一维度有 P0 = ❌）
3. 记录决策（为什么这个标准是这个值）
4. 记录豁免（为什么不验收某项）
```

### 循环阶段

```
验收不通过 → 修复建议交给 fe-artifact → 重新生成 → 重新验收
直到所有 P0 项通过
```

## 入口/出口条件

**入口**：有可运行的前端产物 + DESIGN.md + frontend/modules/*.md
**出口**：验收报告已生成 · 所有 P0 项通过（或用户确认豁免）· 用户确认

## 何时不使用

纯后端 API · 没有设计系统（无视觉标准可比对）· 原型阶段（不需要严格验收）

## 红旗清单

- 只看功能不看视觉 → 强制四维验收
- Token 有硬编码值 → 标记为 P0
- 没测移动端 → 强制多视口检查
- 没测键盘访问 → 强制 Tab 遍历
- 验收标准没有理由 → 强制记录（"为什么是 55fps 不是 60fps？"）
- 有不合格项但没有修复建议 → 强制补充（具体到文件和代码）
- 全部通过但没有决策记录 → 强制补充（为什么这些标准是合理的）

## 验证清单

- [ ] 四个维度是否都判定了？
- [ ] 每个检查项是否有明确的 pass/fail？
- [ ] 未通过项是否有具体修复建议？
- [ ] Token 合规扫描是否执行（无硬编码值）？
- [ ] 多视口截图是否覆盖（375/768/1024/1440）？
- [ ] 键盘遍历是否执行？
- [ ] 性能边界值是否有来源（project.md / 行业基准 / 自定义理由）？
- [ ] 豁免项是否有理由？
- [ ] 决策记录是否完整？
