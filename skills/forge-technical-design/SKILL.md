# Technical Design — 设计阶段（技术层）

## 职责

定义系统的技术架构，包括架构模式、技术选型、服务划分。

**原则**：架构决策不可逆要慎重，组件选择可替换可以大胆。简单方案优先。

## 决策点

### TD1: 架构模式

**问**：
- 读写比是多少？（读多写少 vs 写多读少）
- 一致性要求是什么？（强一致 vs 最终一致）
- 流量和性能要求是什么？（QPS、延迟）
- 团队熟悉什么技术栈？

**记录**：架构模式 + 选择理由 + 被拒方案

### TD2: 技术选型

**问**：
- 团队熟悉什么语言/框架？
- 有什么技术限制？（公司规定、合规要求）
- 生态和文档是否完善？

**记录**：技术栈清单 + 选择理由 + 被拒方案

### TD3: 服务划分

**问**：
- 系统有哪些核心领域？（用户、订单、支付）
- 这些领域之间的耦合度如何？
- 需要独立部署吗？

**记录**：服务清单 + 职责边界 + 通信方式

### TD4: 数据架构

**问**：
- 数据量有多大？（GB、TB）
- 数据关系复杂吗？（一对一、一对多、多对多）
- 需要事务支持吗？

**记录**：数据库选型 + 数据模型 + 索引策略

### TD5: 部署架构

**问**：
- 部署环境是什么？（云、私有化、混合）
- 需要弹性伸缩吗？
- 多区域部署需求？

**记录**：部署环境 + 伸缩策略 + 监控方案

## 文档约束

**project.md 必须包含：**
1. 架构模式（单体/微服务/Serverless + 理由）
2. 技术选型（语言、框架、数据库 + 理由）
3. 服务划分（服务清单 + 职责边界 + 通信方式）
4. 数据架构（数据库选型 + 数据模型 + 索引策略）
5. 部署架构（环境 + 伸缩 + 监控）
6. 性能指标（QPS、延迟、可用性）
7. 安全策略（认证、授权、加密）

**project.md 不应包含：**
- 具体 API 设计（那是 /forge-detail 的事）
- 具体代码实现（那是 生成代码 的事）
- 具体测试用例（那是 写测试 的事）

## 恒久约定

### 架构模式格式
```markdown
## 架构模式

**选择**：单体架构  
**理由**：
- 团队 5 人，微服务运维成本高
- 业务初期，单体足够快速迭代
- 未来可拆分（领域边界清晰）

**被拒方案**：
- 微服务：运维成本高，团队经验不足
- Serverless：不适合长连接场景
```

### 技术选型格式
```markdown
## 技术选型

| 层次 | 选择 | 理由 | 被拒方案 |
|------|------|------|---------|
| 后端语言 | TypeScript | 团队熟悉、类型安全 | Go（学习成本高） |
| 后端框架 | Hono | 轻量、性能好 | Express（性能一般） |
| 前端框架 | React 19 | 生态完善、团队熟悉 | Vue（团队不熟悉） |
| 数据库 | PostgreSQL | 功能强大、运维成熟 | MongoDB（关系复杂） |
```

### 服务划分格式
```markdown
## 服务划分

### 用户服务
- 职责：用户注册、登录、权限管理
- 通信：REST API
- 数据库：PostgreSQL

### 任务服务
- 职责：任务 CRUD、评论、标签
- 通信：REST API
- 数据库：PostgreSQL

### 通知服务
- 职责：邮件、短信、站内信
- 通信：消息队列（RabbitMQ）
- 数据库：Redis（缓存）
```

## 入口/出口条件

**入口条件**：
- 有 interaction-spec.md + DESIGN.md（来自设计阶段）
- 或用户已有交互和视觉设计（跳过设计阶段）

**出口条件**：
- 生成了 project.md
- 架构模式已确定（单体/微服务/Serverless）
- 技术选型已确定（语言、框架、数据库）
- 服务划分已明确（服务清单 + 职责边界）
- 用户确认是否继续（进入 /forge-detail）

## 何时不使用

- 纯前端项目（不需要后端架构）
- 已有完整的技术架构（直接进入 /forge-detail）
- 技术栈已确定（简化技术选型流程）

## 红旗清单

- 没有选择理由 → 强制补充（"为什么选这个？"）
- 过度设计 → 强制简化（"最简单的方案是什么？"）
- 团队不熟悉的技术 → 强制评估（"学习成本多高？"）
- 没有性能指标 → 强制量化（"QPS 多少？延迟多少？"）
- 没有监控方案 → 强制补充（"怎么知道系统正常？"）

## 验证清单

- [ ] 架构模式是否有明确的选择理由？
- [ ] 技术选型是否符合团队经验？
- [ ] 服务划分是否高内聚低耦合？
- [ ] 数据架构是否符合业务需求？
- [ ] 部署架构是否可回滚？
- [ ] 是否有性能指标（QPS、延迟、可用性）？
- [ ] 是否有安全策略（认证、授权、加密）？
