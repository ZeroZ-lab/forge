# Requirements — 定义阶段（需求层）

## 职责

把模糊的业务需求变成可验收的 PRD。每个需求都要有验收条件，不验收的需求 = 不存在的需求。

**原则**：需求不是说"要什么"，是说"不要什么"。边界比功能更重要。

## 决策点

### R1: 用户故事

**问**：
- 作为 [角色]，我想要 [功能]，以便 [价值]
- 这个用户故事的优先级是什么？
- 有没有依赖关系？

**不变原则**：
- 每个用户故事必须包含角色、功能、价值
- 优先级要排序（不是"都很重要"）
- 依赖关系要画清楚（A 依赖 B，B 依赖 C）

**记录**：用户故事列表 + 优先级 + 依赖图

### R2: 验收条件

**问**：
- 怎么知道这个功能做对了？
- 具体的验收标准是什么？
- 边界情况怎么处理？

**不变原则**：
- 验收条件要可测试（不是"用户体验好"，是"3 步内完成任务"）
- 每个用户故事至少 3 个验收条件
- 边界情况要明确（空值、错误、并发）

**记录**：验收条件清单（Given-When-Then 格式）

### R3: 非功能需求

**问**：
- 性能要求是什么？（响应时间、并发数）
- 安全要求是什么？（权限、加密、合规）
- 可用性要求是什么？（SLA、容灾）

**不变原则**：
- 非功能需求要量化（不是"快"，是"< 200ms"）
- 安全需求要提前考虑（不要事后补）
- 可用性要符合业务需求（不是越高越好）

**记录**：性能指标 + 安全要求 + 可用性目标

### R4: 范围排除

**问**：
- 这个版本明确不做什么？
- 哪些功能是"以后再说"？
- 有没有"看起来相关但其实不做"的功能？

**不变原则**：
- 范围排除要写清楚（避免范围蔓延）
- 每个排除的功能都要有理由
- 排除的功能要记录（不是"忘了"，是"决定不做"）

**记录**：排除清单 + 排除理由

### R5: 验收测试

**问**：
- 谁来验收？
- 验收流程是什么？
- 验收不通过怎么办？

**不变原则**：
- 验收人要提前确定（不是"以后再说"）
- 验收流程要可执行（不是"看着办"）
- 验收不通过要有明确的回退方案

**记录**：验收人 + 验收流程 + 回退方案

## 文档约束

**PRD.md 必须包含：**
1. 用户故事列表（按优先级排序）
2. 每个用户故事的验收条件（Given-When-Then 格式）
3. 非功能需求（性能、安全、可用性）
4. 范围排除清单（明确不做什么）
5. 验收计划（谁来验收、怎么验收）
6. 依赖关系图（用户故事之间的依赖）
7. 风险评估（最大的风险是什么）

**PRD.md 不应包含：**
- 交互设计（那是 /forge-design 的事）
- 技术选型（那是 /forge-init 的事）
- 具体实现方案（那是 /forge-detail 的事）

使用 `${CLAUDE_SKILL_DIR}/references/prd-template.md` 作为产出结构参考。

## 恒久约定

### 用户故事格式
```markdown
## 用户故事

### US-01: 创建任务
**作为** 产品经理  
**我想要** 创建任务并分配给团队成员  
**以便** 跟踪项目进度

**优先级**：P0（必须有）  
**依赖**：无

**验收条件**：
- Given 用户在任务列表页，When 点击"新建任务"，Then 弹出创建表单
- Given 用户填写完表单，When 点击"保存"，Then 任务出现在列表中
- Given 任务创建成功，When 查看任务详情，Then 显示创建人和创建时间
```

### 非功能需求格式
```markdown
## 非功能需求

### 性能
- 页面加载时间 < 2s
- API 响应时间 < 200ms（P95）
- 支持 1000 并发用户

### 安全
- 所有 API 需要认证
- 密码加密存储（bcrypt）
- 符合 GDPR 要求

### 可用性
- SLA 99.9%（每月停机 < 43 分钟）
- 数据库主从复制
- 自动故障转移
```

### 范围排除格式
```markdown
## 范围排除

| 功能 | 排除理由 | 后续计划 |
|------|---------|---------|
| 移动端 App | 资源有限，先做 Web | v2.0 考虑 |
| 第三方集成 | MVP 不需要 | v1.5 评估 |
| 高级报表 | 用户未明确需求 | 等用户反馈 |
```

## 入口/出口条件

**入口条件**：
- project.md 的「业务目标」段落已填写（来自 business-alignment）
- 或用户已有明确需求（跳过 business-alignment）

**出口条件**：
- 生成了 PRD.md
- 用户故事已定义（按优先级排序）
- 验收条件已明确（每个用户故事至少 3 个）
- 范围排除已确认（明确不做什么）
- 用户确认是否继续（进入 /forge-design）

## 何时不使用

- 只是技术探索（不需要需求定义）
- 已有完整的 PRD（直接进入 /forge-design）
- 小功能迭代（简化需求流程）

## 红旗清单

- 用户故事没有验收条件 → 强制补充（"怎么知道做对了？"）
- 所有需求都是 P0 → 强制排序（"如果只能做一个呢？"）
- 范围排除清单为空 → 强制思考（"有什么是明确不做的？"）
- 验收条件不可测试 → 重写（"具体怎么验证？"）
- 没有验收人 → 补充（"谁来验收？"）

## 验证清单

- [ ] 用户故事是否按优先级排序？
- [ ] 每个用户故事是否有验收条件（至少 3 个）？
- [ ] 验收条件是否可测试（Given-When-Then 格式）？
- [ ] 非功能需求是否量化（具体数字）？
- [ ] 范围排除是否明确（明确不做什么）？
- [ ] 是否有验收计划（谁来验收、怎么验收）？
- [ ] 依赖关系是否清晰（用户故事之间的依赖）？
