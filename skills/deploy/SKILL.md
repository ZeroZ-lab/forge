# Deploy — 交付阶段

## 职责

规划从代码提交到生产上线的完整发布流程，确保每次发布可逆、可观测、渐进式验证。

**核心洞察**：发布清单是上线前的最后防线。没有回滚方案的发布 = 赌博。好的发布流程 = 可逆（5 分钟回滚）+ 可观测（监控告警）+ 渐进（灰度验证）。

**方法论**：环境 → 容器 → 管道 → 灰度 → 回滚。

## 与上下游的边界

**上游**：读 src/ + tests/（代码和测试）+ testing/test-cases.md（测试用例）+ contract.md（技术选型）
**下游**：deploy/contract.md 交给 DevOps 执行发布

**和 test 的切法**：test 定义测试策略和用例，deploy 定义测试在 CI/CD 中的运行时机和失败策略
**和 codegen 的切法**：codegen 生成代码，deploy 定义代码如何打包、部署、运行

## 方法论：可逆发布

### RL1: 环境（Environment）

确定运行环境——流量模式、运维能力、连接类型。

**核心问题**：流量是稳定还是有峰谷？有运维工程师吗？需要长连接吗（WebSocket/SSE）？

**不变原则**：
- 运维能力决定方案复杂度（没人管就别选复杂的）
- 流量模式决定是否需要弹性伸缩
- 长连接场景排除 Serverless

**记录**：运行环境 + 选择理由 + 被拒方案

### RL2: 容器（Container）

确定容器化和编排方案——服务数量、扩缩容需求、团队经验。

**核心问题**：除了主应用还有几个服务？（数据库、缓存、消息队列）需要自动扩缩容吗？团队对容器编排有经验吗？

**不变原则**：
- 服务数量决定编排复杂度（1 个服务不需要 K8s）
- 本地开发环境必须和生产一致（"在我机器上能跑" = 环境问题）
- 不要为了解决不存在的问题引入复杂度

**记录**：容器方案 + 服务清单 + 选择理由 + 被拒方案

### RL3: 管道（Pipeline）

确定 CI/CD 流水线——代码托管、部署平台、审批流程、回滚速度。

**核心问题**：代码托管在哪？部署到哪个云平台？上线前需要人工审批吗？出问题了需要多快回滚？

**不变原则**：
- 手动部署 = 人为事故高发区（必须自动化）
- CI/CD 平台由代码托管位置决定（减少集成复杂度）
- 回滚速度决定事故影响范围（< 5 分钟是目标）

**记录**：CI/CD 平台 + Pipeline 阶段 + 选择理由 + 被拒方案

### RL4: 灰度（Canary）

确定环境管理和灰度策略——环境数量、发布频率、验证需求。

**核心问题**：团队几个人？发布频率多高？（每次提交/每天/每周）有"先验证再上线"的需求吗？多区域部署？

**不变原则**：
- 至少 2 个环境（staging + prod），没有例外
- 发布频率越高，越需要自动化验证和灰度
- 环境越多运维成本越高，按需求选择（不要过度设计）

**记录**：环境清单 + 各环境触发条件 + 灰度比例 + 选择理由 + 被拒方案

### RL5: 回滚（Rollback）

确定回滚方案和监控告警——触发条件、回滚命令、告警渠道。

**核心问题**：出了问题怎么第一时间知道？（用户反馈 vs 系统告警）有监控预算吗？需要追踪什么？（错误率/响应时间/业务指标）

**不变原则**：
- 没有监控的系统 = 出了问题靠用户反馈（太晚了）
- 健康检查是最低要求，不是可选项
- 告警太多 = 没有告警（告警疲劳）
- 回滚步骤必须是具体命令，不是"按回滚按钮"

**记录**：监控方案 + 告警渠道 + 健康检查端点 + 回滚命令 + 选择理由 + 被拒方案

## AI 的角色

| 阶段 | AI 角色 | 行为 |
|------|---------|------|
| 环境 | 运维能力评估者 | 从团队规模和运维经验推导环境方案复杂度 |
| 容器 | 架构复杂度分析者 | 从服务数量推导容器编排方案 |
| 管道 | 流水线设计者 | 从代码托管和部署平台推导 CI/CD 配置 |
| 灰度 | 发布策略设计者 | 从发布频率推导环境管理和灰度比例 |
| 回滚 | 事故响应设计者 | 从监控需求推导告警和回滚方案 |

## 引导技巧

**环境判断**："这个系统挂了，谁第一个知道？"——没有监控就强制补充
**容器判断**："本地能跑和生产一样的环境吗？"——不能就强制容器化
**管道判断**："手动部署出过事故吗？"——出过就强制自动化
**灰度判断**："发布后发现问题，多久能回滚？"——超过 5 分钟就强制优化
**回滚判断**："回滚步骤是什么？"——"按按钮"不算具体命令

## 产出结构

```
docs/features/<feature>/deploy/
├── contract.md      # RL1-RL5 决策 + 部署流程 + 回滚方案 + 监控告警
└── changelog.md
```

## 文档约束

**deploy/contract.md 必须包含**：RL1-RL5 决策（选择+理由+被拒）· 部署流程（从提交到上线）· 环境变量清单 · 健康检查端点 · 回滚步骤（具体命令）· 发布清单模板
**deploy/contract.md 不应包含**：具体代码实现（codegen）· 具体测试用例（test-cases）· 业务需求（feature 级 contract.md）

## 模板

使用 `${CLAUDE_SKILL_DIR}/references/release-template.md` 作为产出结构参考。

## 入口/出口条件

**入口**：有 src/ + tests/ + testing/test-cases.md（或用户已有代码和测试）· review 代码审查通过（subagent 独立审查，如有）
**出口**：deploy/contract.md 已生成 · 部署流程已定义 · 回滚步骤已明确（具体命令）· 监控告警已配置 · 发布清单已就绪

## 运行时信号

- 输入：code review passed、test results
- 输出：release plan、rollback plan、release blocked
- 路由：详见 `registry.yaml` 的 `forge-deploy` 节点；本节只保留人类可读摘要。
- 升级：无回滚方案 · 无健康检查 · 无监控告警

## 何时不使用

纯本地工具 · 已有完整 CI/CD · 原型验证阶段

## 红旗清单

- 没有回滚方案 → 强制补充（"具体命令是什么？"）
- 没有健康检查 → 强制补充（"怎么知道系统正常？"）
- 手动部署 → 强制自动化（"手动步骤 = 人为事故"）
- 只有一个环境 → 强制补充（"至少 staging + prod"）
- 没有监控 → 强制补充（"出问题谁第一个知道？"）
