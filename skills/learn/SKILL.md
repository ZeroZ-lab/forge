# Learn — 进化阶段

## 职责

从积累的偏差信号中发现 skill 方法论的系统性缺陷，提出修正建议。

**核心洞察**：单次偏差可能是偶发，同类偏差高频出现说明方法论有盲区。learn 是慢回路的执行者——消费偏差归因，产出方法论改进。

**方法论**：聚合 → 模式 → 建议 → 验证。

## 与上下游的边界

**上游**：review 报告的偏差归因 · changelog 的变更记录 · timeline 的方法论进化历史
**下游**：skill 修改建议 · timeline 追加进化记录

**和 review 的切法**：review 归因单个项目的偏差，learn 聚合多个项目的偏差模式
**和 skill 维护的切法**：learn 提出修改建议 + 证据，人类确认后执行修改

## 方法论：聚合→模式→建议→验证

### L1: 聚合（Aggregate）

收集所有可获得的偏差信号，按归因分类。

**数据源**：
- review 报告的「归因汇总」表（主要来源）
- changelog 中的文档修正记录（间接信号：频繁修正 = 方法论不清晰）
- timeline 中的方法论进化历史（避免重复改进）

**不变原则**：
- 只看有归因标记的偏差——无归因的问题不是 learn 的输入
- 一条偏差不是模式，三条以上同类偏差才值得关注
- 区分"高频出现"和"偶发"——频率是信号，单次是噪声

### L2: 模式（Pattern）

从聚合数据中识别系统性模式。

**核心问题**：哪些偏差高频出现？它们集中在哪个 skill 的哪个决策点？

**不变原则**：
- 模式 = 同类偏差 ≥ 3 次，或跨项目出现同类偏差
- 按 skill × 决策点分组——同一 skill 的不同决策点分开统计
- 如果偏差集中在某个决策点 → 决策点不够细
- 如果偏差散布在多个决策点 → 缺少决策点

### L3: 建议（Recommend）

把模式转化为具体的 skill 修改建议。

**核心问题**：怎么改 skill 才能消除这个模式？改哪个决策点？

**不变原则**：
- 每条建议必须可执行——指向具体的 SKILL.md 具体位置
- 建议要有证据链（哪些偏差记录支撑了这个建议）
- 建议要包含反面验证（"如果不改会怎样"）

**反向验证**：如果之前因同类偏差修改过 skill，但偏差仍然出现 → 说明上次归因错误，应回滚修改并重新归因。避免 skill 无限膨胀。

**排序规则**：先处理跨项目高频、会导致错误投影或阻塞发布的模式；再处理单项目高频；最后处理清晰度问题。同等证据强度下，优先改 shared rubric / red flag / output contract，再改具体 skill，避免把每个 skill 都塞成完整 MAPE-K 模板。

### L4: 验证（Verify）

自我检查建议不会引入新问题。

**核心问题**：修改后会不会和已有方法论冲突？会不会让 skill 超 200 行？

**不变原则**：
- 新建议不能和已有不变原则矛盾
- 如果加内容导致超行 → 考虑提取 protocol 文件
- 修改后跑 validate.mjs 验证

## AI 的角色

| 阶段 | AI 角色 | 行为 |
|------|---------|------|
| 聚合 | 数据收集者 | 读所有 review 报告和 changelog，提取偏差归因 |
| 模式 | 模式识别者 | 按 skill × 决策点分组，找出高频模式 |
| 建议 | 方案设计者 | 提出具体修改 + 证据链 + 反面验证 |
| 验证 | 自我审查者 | 检查冲突、行数、validate 通过 |

## 文档约束

**产出**：skill 修改建议 + 证据链，不直接修改 skill（人类确认后执行）。

## 入口/出口条件

**入口**：review 报告累积了 ≥ 3 条同类 skill 归因 · 或跨项目出现同类偏差 · 或用户主动触发
**出口**：修改建议已输出 · 证据链已附 · 用户确认 → 执行修改 → timeline 追加进化记录

## 运行时信号

- 输入：same-class deviation >= 3、cross-project deviation
- 输出：methodology change proposal、evidence chain
- 路由：详见 `registry.yaml` 的 `forge-learn` 节点；本节只保留人类可读摘要。
- 升级：证据不足 · 建议会导致 skill 膨胀或冲突

## 触发条件

- 某类 skill 归因累积 3+ 条
- 用户说"复盘"、"回顾方法论"、"skill 有什么问题"

## 红旗

- 没有证据就建议修改 → 强制补充证据链
- 单次偏差就认为有问题 → 强制要求 ≥ 3 条同类
- 建议和已有方法论冲突 → 强制检查兼容性

## 验证清单

- [ ] 是否有 ≥ 3 条同类偏差归因作为输入？
- [ ] 模式是否按 skill × 决策点分组？
- [ ] 每条建议是否指向具体 SKILL.md 具体位置？
- [ ] 每条建议是否有证据链？
- [ ] 建议是否通过自我验证（无冲突、不超行）？

## 历史维护（自动）

执行方法论修改后追加 `docs/timeline.md`：`### {日期} — 方法论进化 · 修改：{skill} {具体变更} · 触发：{N} 条同类偏差`。超 100 行时归档。

## 完成提示

```
✅ 方法论进化分析完成！

发现 {N} 个模式，提出 {M} 条修改建议。

下一步：
  确认建议       — 执行 skill 修改
  继续积累       — 等更多偏差数据再分析
```
