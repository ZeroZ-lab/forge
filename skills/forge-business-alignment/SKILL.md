# Business Alignment — 定义阶段（业务层）

## 职责

在写代码之前验证假设，确保"做的东西"和"要解决的问题"对齐。

**原则**：先验证需求再验证方案。最贵的错误是做了没人用的东西。

## 决策点

### BA1: 需求验证

**问**：
- 这个问题现在怎么解决的？
- 有多少人遇到这个问题？
- 他们愿意为解决这个问题付费吗？（时间/金钱）

**不变原则**：
- 没有现有解决方案 = 问题可能不痛
- 用户说的需求 ≠ 真实需求（观察行为，不要只听嘴说）
- 验证要快，不要花 3 个月调研

**记录**：需求来源 + 验证方法 + 验证结果

### BA2: 目标用户

**问**：
- 谁会用这个产品？
- 他们的工作流程是什么？
- 他们在什么场景下使用？

**不变原则**：
- 目标用户要具体（不是"所有人"）
- 用户画像要有名字（"张三，35 岁，产品经理"）
- 场景要具体（不是"日常使用"，是"每周五下午写周报"）

**记录**：用户画像 + 使用场景 + 痛点地图

### BA3: MVP 范围

**问**：
- 最小可以是什么？
- 如果没有这个功能，产品还能成立吗？
- 哪些功能是"锦上添花"？

**不变原则**：
- MVP 要小到可以在 2 周内验证
- 每个功能都要回答"没有它就不成立吗？"
- 边界要画清楚（做什么 vs 不做什么）

**记录**：MVP 功能清单 + 边界声明 + 延后功能

### BA4: 成功标准

**问**：
- 怎么知道这个产品成功了？
- 具体的数字指标是什么？
- 什么时候评估？

**不变原则**：
- 成功标准要可量化（不是"用户喜欢"，是"日活 > 1000"）
- 指标要少而精（3-5 个核心指标）
- 评估时间要明确（不是"以后再说"）

**记录**：核心指标 + 目标值 + 评估时间

### BA5: 资源约束

**问**：
- 团队有多少人？多少时间？
- 预算是多少？
- 有哪些技术限制？

**不变原则**：
- 资源决定范围，不是范围决定资源
- 时间是最重要的约束
- 技术限制要提前暴露（不要做到一半才发现不行）

**记录**：团队规模 + 时间约束 + 预算 + 技术限制

## 文档约束

**合入 project.md 的「业务目标」段落，不生成独立文件。**

必须包含：
1. 需求验证结果（痛点是否真实）
2. 目标用户画像（3-5 个典型用户）
3. MVP 范围（做什么 + 不做什么）
4. 成功标准（3-5 个可量化指标）
5. 资源约束（团队、时间、预算、技术）

不应包含：
- 具体功能列表（那是 /forge-requirements 的事）
- 交互设计（那是 /forge-design 的事）
- 技术选型（那是 /forge-init 的事）

## 模板

使用 `${CLAUDE_SKILL_DIR}/references/project-template.md` 作为 project.md 结构参考。

## 恒久约定

### 用户画像格式
```markdown
## 用户画像

### 张三（产品经理）
- 年龄：35 岁
- 工作内容：需求管理、项目跟踪
- 痛点：每周花 3 小时手动同步数据
- 使用场景：每周五下午写周报
- 期望：自动化数据同步，节省时间
```

### 成功标准格式
```markdown
## 成功标准

| 指标 | 当前值 | 目标值 | 评估时间 |
|------|--------|--------|---------|
| 日活用户 | 0 | 1000 | 上线后 3 个月 |
| 任务完成率 | N/A | >80% | 上线后 1 个月 |
| 用户满意度 | N/A | >4.5/5 | 上线后 2 个月 |
```

### MVP 范围格式
```markdown
## MVP 范围

**核心功能**（必须有）：
- 功能 1：...
- 功能 2：...

**边界声明**（明确不做）：
- 不做 X，因为...
- 不做 Y，因为...

**延后功能**（以后再做）：
- 功能 A：等 MVP 验证后再做
- 功能 B：等资源允许时再做
```

## 入口/出口条件

**入口条件**：
- 有 idea-brief.md（来自 /forge-brainstorm）
- 或用户已有明确方向（跳过 brainstorm）

**出口条件**：
- project.md 的「业务目标」段落已填写
- 需求已验证（痛点真实）
- MVP 范围已确认
- 成功标准已定义
- 用户确认是否继续（进入技术选型 + 设计系统）

## 何时不使用

- 只是技术探索（不需要业务验证）
- 已有完整的 PRD（直接进入 /forge-design）
- 内部工具，不需要市场验证（简化验证流程）

## 红旗清单

- 用户说"所有人都需要" → 强制具体化（"给我 3 个典型用户"）
- 成功标准模糊 → 强制量化（"具体数字是什么？"）
- MVP 太大 → 强制砍功能（"如果只能做一个呢？"）
- 没有验证方法 → 补充"怎么知道这个假设是对的？"
- 资源无限 → 强制约束（"如果只有 2 周呢？"）

## 验证清单

- [ ] 需求是否已验证（痛点真实）？
- [ ] 目标用户是否具体（有名字、有场景）？
- [ ] MVP 是否小到可以在 2 周内验证？
- [ ] 成功标准是否可量化（3-5 个指标）？
- [ ] 资源约束是否明确（团队、时间、预算）？
- [ ] 是否有风险评估？
- [ ] 下一步行动是否清晰？
