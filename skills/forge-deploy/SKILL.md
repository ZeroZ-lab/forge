# Deploy — 交付阶段

## 职责

规划从代码提交到生产上线的完整发布流程，确保每次发布可逆、可观测、渐进式验证。

**原则**：发布清单 = 上线前的最后防线。没有回滚方案 = 不允许发布。

## 决策点

### RL1: 运行环境

**问**：
- 流量是稳定的还是有明显的峰谷？（白天多晚上少 / 活动突发）
- 有运维工程师吗？还是开发者自己管？
- 需要长时间保持连接吗？（WebSocket / SSE / 后台任务）

**不变原则**：
- 运维能力决定方案复杂度（没人管就别选复杂的）
- 流量模式决定是否需要弹性伸缩
- 长连接场景排除 Serverless

**记录**：运行环境 + 选择理由 + 被拒方案

### RL2: 容器化

**问**：
- 除了主应用，还有几个服务要一起跑？（数据库、缓存、消息队列、Worker）
- 需要自动扩缩容吗？
- 团队对容器编排工具有经验吗？

**不变原则**：
- 服务数量决定编排复杂度
- 本地开发环境必须和生产一致（"在我机器上能跑" = 环境问题）
- 不要为了解决不存在的问题引入复杂度

**记录**：方案 + 服务清单 + 选择理由 + 被拒方案

### RL3: CI/CD

**问**：
- 代码托管在哪里？
- 部署到哪个云平台？
- 上线前需要人工审批吗？
- 出问题了需要多快回滚？

**不变原则**：
- 手动部署 = 人为事故高发区
- CI/CD 平台由代码托管位置决定（减少集成复杂度）
- 回滚速度决定事故影响范围

**记录**：平台 + Pipeline 阶段 + 选择理由 + 被拒方案

### RL4: 环境管理

**问**：
- 团队几个人？
- 发布频率多高？（每次提交 / 每天 / 每周 / 每月）
- 有"先验证再上线"的需求吗？
- 多区域部署需求？

**不变原则**：
- 至少 2 个环境（staging + prod），没有例外
- 发布频率越高，越需要自动化验证
- 环境越多运维成本越高，按需求选择

**记录**：环境清单 + 各环境触发条件 + 选择理由 + 被拒方案

### RL5: 监控告警

**问**：
- 出了问题怎么第一时间知道？（用户告诉你 vs 系统告警）
- 有监控预算吗？
- 需要追踪什么？（错误率 / 响应时间 / 业务指标）

**不变原则**：
- 没有监控的系统 = 出了问题靠用户反馈
- 健康检查是最低要求，不是可选项
- 告警太多 = 没有告警（告警疲劳）

**记录**：方案 + 告警渠道 + 健康检查端点 + 选择理由 + 被拒方案

## 文档约束

**deploy/contract.md 必须包含：**
1. RL1-RL5 决策（每个选择 + 理由 + 被拒方案）
2. 技术选型表（运行环境、容器、CI/CD、监控）
3. 部署流程（从代码提交到上线的步骤）
4. 环境变量清单（名称 + 用途 + 是否敏感）
5. 健康检查端点
6. 回滚步骤（具体命令，不是"按回滚按钮"）
7. 发布清单模板（上线前 checklist）

**deploy/contract.md 不应包含：**
- 具体代码实现（那是 生成代码 的事）
- 具体测试用例（那是 写测试 的事）
- 业务需求（那是 feature 级 contract.md 的事）

## 恒久约定

### 发布清单格式
```markdown
## 发布清单

### 发布前
- [ ] 所有测试通过（CI 绿灯）
- [ ] 数据库迁移已审核
- [ ] 环境变量已配置
- [ ] 回滚方案已确认
- [ ] 值班人员已安排

### 发布中
- [ ] 灰度比例已设置（10% → 50% → 100%）
- [ ] 监控面板已打开
- [ ] 错误率未上升

### 发布后
- [ ] 健康检查通过
- [ ] 核心功能验证
- [ ] 性能指标正常
- [ ] 无异常告警
```

### 回滚步骤格式
```markdown
## 回滚步骤

### 触发条件
- 错误率 > 1%
- P99 延迟 > 2s
- 健康检查连续失败 3 次

### 回滚命令
1. 回滚部署：`kubectl rollout undo deployment/app`
2. 回滚数据库：`npm run db:rollback`
3. 验证回滚：`curl https://api.example.com/health`
4. 通知团队：Slack #incidents

### 回滚后
- 创建事故报告
- 分析根因
- 修复后重新走发布流程
```

### 环境变量格式
```markdown
## 环境变量

| 变量名 | 用途 | 敏感 | 默认值 |
|--------|------|------|--------|
| DATABASE_URL | 数据库连接 | 是 | — |
| REDIS_URL | 缓存连接 | 是 | — |
| LOG_LEVEL | 日志级别 | 否 | info |
| NODE_ENV | 运行环境 | 否 | production |
```

## 入口/出口条件

**入口条件**：
- 有 src/ + tests/（来自 生成代码）
- 有 test-cases.md（来自 写测试）
- 或用户已有代码和测试（跳过 build 和 test）

**出口条件**：
- 生成了 deploy/contract.md
- 部署流程已定义（从提交到上线）
- 回滚步骤已明确（具体命令）
- 监控告警已配置
- 发布清单模板已就绪

## 何时不使用

- 纯本地工具（不需要部署）
- 已有完整 CI/CD（直接进入验证）
- 原型验证阶段（简化部署流程）

## 红旗清单

- 没有回滚方案 → 强制补充（"出问题怎么回滚？具体命令是什么？"）
- 没有健康检查 → 强制补充（"怎么知道系统正常？"）
- 手动部署 → 强制自动化（"手动步骤 = 人为事故"）
- 只有一个环境 → 强制补充（"至少 staging + prod"）
- 没有监控 → 强制补充（"出问题谁第一个知道？"）
