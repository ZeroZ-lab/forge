# Deploy Design — 决策协议

## 职责

引导人类完成部署设计的 5 个决策点。

**原则**：Skill 只问业务问题。技术问题模型自己搜索、自己评估。

每个决策点：
1. 问业务问题（只有人类能回答的）
2. 根据回答，搜索最新技术方案，生成 2-3 个选项 + 各自代价
3. 给出推荐 + 理由
4. 等人类确认
5. 记录选择 + 理由 + 被拒方案

## 产出结构

```
docs/features/<feature>/deploy/
├── contract.md      # DP1-DP5 决策 + 部署流程 + 环境变量（~60 行）
└── changelog.md
```

---

## 方法论：可逆部署

部署设计的核心方法论：

1. **可回滚** — 每次部署都必须能快速回到上一个版本
2. **可观测** — 部署后必须能知道系统是否正常
3. **渐进式** — 变更通过多个环境逐步验证，不一步到生产

每个决策点都是这套方法论的一个切面。

## 决策点

### DP1: 运行环境

**问人类：**
- 流量是稳定的还是有明显的峰谷？（白天多晚上少 / 活动突发）
- 有运维工程师吗？还是开发者自己管？
- 需要长时间保持连接吗？（WebSocket / SSE / 后台任务）

**不变原则：**
- 运维能力决定方案复杂度（没人管就别选复杂的）
- 流量模式决定是否需要弹性伸缩
- 长连接场景排除 Serverless

**记录**：运行环境 + 基础镜像/运行时 + 选择理由 + 被拒方案

---

### DP2: 容器化方案

**问人类：**
- 除了主应用，还有几个服务要一起跑？（数据库、缓存、消息队列、Worker）
- 需要自动扩缩容吗？
- 团队对容器编排工具有经验吗？

**不变原则：**
- 服务数量决定编排复杂度
- 本地开发环境必须和生产一致（"在我机器上能跑" = 环境问题）
- 不要为了解决不存在的问题引入复杂度

**记录**：方案 + 服务清单 + 选择理由 + 被拒方案

---

### DP3: CI/CD

**问人类：**
- 代码托管在哪里？
- 部署到哪个云平台？
- 上线前需要人工审批吗？
- 出问题了需要多快回滚？

**不变原则：**
- 手动部署 = 人为事故高发区
- CI/CD 平台由代码托管位置决定（减少集成复杂度）
- 回滚速度决定事故影响范围

**记录**：平台 + Pipeline 阶段 + 选择理由 + 被拒方案

---

### DP4: 环境管理

**问人类：**
- 团队几个人？
- 发布频率多高？（每次提交 / 每天 / 每周 / 每月）
- 有"先验证再上线"的需求吗？
- 多区域部署需求？

**不变原则：**
- 至少 2 个环境（staging + prod），没有例外
- 发布频率越高，越需要自动化验证
- 环境越多运维成本越高，按需求选择

**记录**：环境清单 + 各环境触发条件 + 选择理由 + 被拒方案

---

### DP5: 监控

**问人类：**
- 出了问题怎么第一时间知道？（用户告诉你 vs 系统告警）
- 有监控预算吗？
- 需要追踪什么？（错误率 / 响应时间 / 业务指标）

**不变原则：**
- 没有监控的系统 = 出了问题靠用户反馈
- 健康检查是最低要求，不是可选项
- 告警太多 = 没有告警（告警疲劳）

**记录**：方案 + 告警渠道 + 健康检查端点 + 选择理由 + 被拒方案

---

## 文档约束

产出必须包含：
1. **DP1-DP5 决策**：每个选择 + 理由 + 被拒方案
2. **技术选型表**
3. **部署流程**：从代码提交到上线的步骤
4. **环境变量清单**
5. **健康检查端点**

---

## 恒久约定

### 容器规范
- 多阶段构建（build → production）
- 非 root 用户运行
- 排除无关文件

### 环境变量命名
- 大写 SNAKE_CASE
- 按前缀分组
- 敏感值不入代码

### 健康检查
```
GET /health → 200 { status: "ok", version: "..." }
```
- 检查核心依赖连通性
- 不检查外部服务（避免级联失败）
