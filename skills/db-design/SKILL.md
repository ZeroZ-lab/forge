# Database Design — 决策协议

## 职责

引导人类完成数据库设计的 5 个决策点。

**原则**：Skill 只问业务问题。技术问题模型自己搜索、自己评估。

每个决策点：
1. 问业务问题（只有人类能回答的）
2. 根据回答，搜索最新技术方案，生成 2-3 个选项 + 各自代价
3. 给出推荐 + 理由
4. 等人类确认
5. 记录选择 + 理由 + 被拒方案

## 产出结构

```
docs/features/<feature>/database/
├── contract.md      # DB1-DB5 决策 + 索引规划 + 迁移规则（~80 行）
└── changelog.md
```

---

## 方法论：数据模型驱动

数据库设计的核心方法论：

1. **模型先行** — 先理清实体和关系，再选存储
2. **查询驱动索引** — 索引为查询服务，不是为字段服务
3. **迁移可逆** — 每次变更都必须能回滚

每个决策点都是这套方法论的一个切面。

## 决策点

### DB1: 数据库选型

**问人类：**
- 数据量大概会增长到多少？
- 数据之间的关系复杂吗？（多层嵌套 / 图关系 / 简单父子）
- 有强一致性事务需求吗？（比如：转账必须原子操作）
- 团队有运维过什么数据库的经验？

**不变原则：**
- 关系型 vs 非关系型由**数据关系复杂度**决定，不是偏好
- 团队能运维的 > 技术上最先进的
- 选型一旦确定，迁移成本极高

**记录**：数据库 + 版本 + 选择理由 + 被拒方案

---

### DB2: ID 策略

**问人类：**
- 会有多个服务/节点同时写同一张表吗？
- ID 会暴露在 URL 中吗？用户能从中推断出什么？（比如：你是第 N 个用户）
- 数据量会大到需要关注存储效率吗？

**不变原则：**
- 暴露自增 ID = 暴露业务量 + 可枚举攻击面
- 分布式写入需要无协调 ID 方案
- 时间有序性影响排序查询性能

**记录**：ID 方案 + 存储类型 + 选择理由 + 被拒方案

---

### DB3: 索引策略

**问人类：**
- 查询模式在设计阶段能确定吗？
- 写入量大吗？（索引越多写入越慢）
- 有没有"查得慢就加索引"的运维习惯？

**不变原则：**
- 索引为查询服务，不为字段服务
- 每个索引都有写入成本，不要无脑加
- 复合索引的列顺序决定它能服务哪些查询

**记录**：策略 + 索引规划表 + 选择理由 + 被拒方案

---

### DB4: 迁移策略

**问人类：**
- schema 变更频繁吗？（早期迭代 vs 稳定期）
- 多人同时开发时，schema 冲突怎么处理？
- 生产环境的迁移需要审批吗？

**不变原则：**
- schema 变更必须版本化，和代码一起提交
- 迁移必须可回滚（不能只有 up 没有 down）
- 生产迁移前必须在 staging 验证

**记录**：工具 + 迁移规则 + 选择理由 + 被拒方案

---

### DB5: 软删除策略

**问人类：**
- 删除的数据需要恢复吗？
- 有数据保留的合规要求吗？（审计 / GDPR 遗忘权）
- 删除一条记录时，它关联的数据怎么处理？

**不变原则：**
- 有恢复需求 → 软删除
- 有合规删除需求 → 物理删除（GDPR 要求真正删除）
- 两者可以共存：先软删除，过期后物理清理

**记录**：策略 + 适用表清单 + 选择理由 + 被拒方案

## 文档约束

产出必须包含：
1. **DB1-DB5 决策**：每个选择 + 理由 + 被拒方案
2. **表清单**：引用 api/ 共享数据模型
3. **索引规划表**：表名 + 索引名 + 列 + 用途
4. **迁移规则**：变更流程

## 恒久约定

### 命名规范
- 表名：snake_case 复数
- 列名：snake_case
- 索引名：`{表名}_{列名}_idx`

### 通用列
每张表都包含：
```
id: primary key
created_at: timestamp, not null, default now()
updated_at: timestamp, not null, default now()
```
