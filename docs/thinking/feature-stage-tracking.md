## 问题重构

**原始问题**：
> Forge 缺少阶段追踪，多 feature 时更要考虑

**追问过程**：
1. Why 需要追踪？→ 多 feature 并行时不知道整体进展
2. Why 不知道？→ 状态散落各 feature 目录，无聚合点
3. Why 无聚合点？→ Forge 设计哲学是"文档即状态"——文件存在=阶段完成
4. Why 文件存在不够？→ 三个盲区：进行中vs未开始、跳过vs未到、依赖vs独立
5. Why 这三个盲区重要？→ 多 feature 并行的核心问题是**协调**——feature B 被 feature A 的产物阻塞

**重构后的问题**：
> Forge 需要一个轻量级协调层，让多 feature 并行开发时的状态、阻塞和依赖关系可见，同时不破坏"文档即状态"的设计哲学。

## 假设清单

| # | 假设 | 确定度 | 验证方法 | 如果不成立 |
|---|------|--------|---------|-----------|
| H1 | 用户会同时开发多个 feature | 可能 | 看实际项目有几个 feature 目录 | 单 feature 追踪就够 |
| H2 | Feature 之间有依赖关系 | 可能 | 看现有项目是否有跨 feature 引用 | 依赖追踪是过度设计 |
| H3 | AI 每次 skill 完成时会更新 status.md | 不确定 | 实际使用观察 | 需要自动化机制而非手动 |
| H4 | 用户需要全局视图 | 确定 | 用户明确提出 | 每个 feature 独立就够了 |
| H5 | status.md 不会膨胀 | 可能 | 10 feature × 12 阶段 | 需要压缩或分层 |

**最脆弱的假设**：H3 — AI 是否每次都执行更新。过时的状态比没有状态更危险。

## 分析过程

### First Principles

Forge 的阶段本质上是一个**有限状态机**：

- 状态：未开始 · 进行中 · 完成 · 跳过 · 阻塞
- 转换触发：skill 完成（出口条件满足）
- 转换动作：更新 status.md + 追加 timeline + 追加 changelog

多 feature 的状态机**独立但有耦合**——耦合点不是阶段本身，而是产物依赖（B 的 detail 需要 A 的 api/contract.md）。

### 因果链

```
多 feature 并行 → feature 间有产物依赖 → 需要知道被依赖 feature 的阶段
→ 需要全局状态视图 → 需要一个文件聚合所有 feature 的状态 → status.md
```

### 被否方案及理由

| 方案 | 理由 |
|------|------|
| 扩展现有 project.md Feature 索引 | project.md 职责已重，pre-init 阶段可能不存在 |
| 每个 feature 目录加 status.md | 分布式无全局视图，依赖检查需读多个文件 |
| YAML/JSON 状态文件 | 不人类可读，违背 Forge 的文档哲学 |

### 关键 trade-off：中心化 vs 分布式

Forge 使用场景是单用户/小团队 + AI session 串行执行——不存在真正并发写入。中心化更好。

### 膨胀分析

| feature 数 | 总行数 | 判定 |
|-----------|--------|------|
| 3 | ~30 行 | ✅ 安全 |
| 10 | ~60 行 | ✅ 安全 |
| 30 | ~120 行 | ⚠️ 需归档已交付 |
| 100 | ~350 行 | ❌ 需分组 |

## 结论

**判断**：docs/status.md 是正确方向，需要三个设计约束：
1. 状态机语义明确（5 种状态 + 转换条件）
2. 自动更新机制（写入每个 skill 的历史维护段）
3. 依赖 = 产物依赖（具体的文件级依赖，不是抽象关系）

**置信度**：高

**依据**：状态机模型精确匹配 Forge 阶段结构；串行场景下中心化无并发问题；膨胀在合理范围内

**前提依赖**：如果团队扩大到多人并发执行（H1 变化），需要分布式方案。如果 AI 经常忘记更新（H3 不成立），需要在 review skill 加一致性检查。
