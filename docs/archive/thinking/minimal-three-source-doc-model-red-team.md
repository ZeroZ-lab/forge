## 问题重构

**原始问题**：
> 对“project.md + goal.md + CU”三事实源模型做最强、有理有据的抨击。

**追问过程**：
1. Why：为什么想减少文件？因为重复、漂移和上下文成本。
2. Why：为什么会重复？因为文件按阶段命名，却没有严格唯一权威和独立消费者。
3. Why：减少文件一定能解决吗？不能；它可能只是把不同更新周期和不同读者的信息塞进大文件。

**重构后的问题**：
> 如何在不制造文档数量崇拜的前提下，最小化重复，同时保留独立消费者、独立更新周期和独立验证责任？

## 假设清单

| # | 假设 | 确定度 | 验证方法 | 如果不成立 |
|---|------|--------|---------|-----------|
| H1 | 一个 goal.md 能同时服务产品、设计、工程、测试和发布 | 不确定 | 用复杂前端、迁移和合规 feature 做盲测 | 必须允许按责任拆分 |
| H2 | CU 能承载完整验证证据且保持可读 | 可能 | 检查 20 次迭代后的 CU 大小和检索成本 | 需要机器证据与人类摘要分离 |
| H3 | modules/*.md 足以吸收所有复杂度 | 不确定 | 用跨模块流程、发布编排、测试矩阵验证 | 需要独立的跨模块文档 |
| H4 | 下游 Agent 能可靠定位大文档中与自己相关的段落 | 不确定 | 比较单大文件和按需文档的 token/错误率 | 需要更窄的读取 interface |
| H5 | 所有项目都能接受同一最小文件集合 | 不确定 | 在 CLI、SaaS、医疗、基础设施项目对比 | 必须按风险自适应 |

**最脆弱的假设**：H1。不同角色读取的是不同稳定性、粒度和验证语义，把它们合并不会消除复杂度，只会隐藏复杂度。

## 分析过程

### Steelman

三事实源模型的最强版本是：

- `project.md` 保存跨 feature 的长期约束；
- `goal.md` 保存单 feature 的全部交付合约；
- `CU` 保存一次变更的全部历史与验证证据；
- `modules/*.md` 仅在复杂时下钻；
- 其他文件都是临时投影，不默认持久化。

它显著减少重复、漂移、检索路径和模板维护成本。

### Red Team

#### 1. 它优化了文件数量，而不是认知 interface

一个 300 行 `goal.md` 仍然可能要求测试 Agent、前端 Agent、发布 Agent读取大量无关内容。文件少不等于 interface 小；真正指标应是完成任务必须理解多少信息。

#### 2. 它把独立更新周期错误地合并

业务 AC、交互状态、模块 interface、测试风险和发布回滚的变化频率不同。合并后任何局部变化都会触碰同一文件，制造冲突、审查噪音和所有权模糊。

#### 3. 它削弱独立审查

如果定义、设计、测试策略都在 goal 中由同一个 Agent 连续生成，review 更容易验证内部一致性，而不是发现同源错误。独立文档有时不是重复，而是不同角色的独立判断结果。

#### 4. 它使完成条件膨胀

goal 同时承担目标、业务 AC、交互、技术约束、测试和发布时，“修改 goal”不再表达清晰语义。读者无法快速判断某次 diff 是需求变化、技术决策变化还是发布约束变化。

#### 5. CU 会变成事实垃圾桶

如果 CU 同时承载决策、文件变化、验证日志、review、回滚和证据，它会迅速变成长篇交付档案。其 interface 接近 implementation，成为另一个 shallow document。

#### 6. modules 无法表达跨模块问题

测试策略、用户流程和发布计划常常横跨多个 module。强行写入某个 module 会破坏归属；写回 goal 又导致 goal 继续膨胀。

#### 7. “按需拆分”缺少可执行门槛

没有机器可检查的拆分条件时，不同 Agent 会做出不同选择。同类项目会出现完全不同的文档形状，降低可预测性和 benchmark 能力。

#### 8. 它对高风险项目不成立

安全、支付、迁移、医疗或合规项目需要独立测试证据、发布审批和责任分离。把这些降为 goal 的章节，会损害审计性，而不是提升质量。

### Premortem

假设一年后失败：

1. goal 平均超过 250 行，Agent 开始只读首段并漏掉测试/发布约束。
2. 产品修改 AC 时误触技术段落，工程修改 interface 时顺手改写业务断言。
3. CU 大量增长但无人阅读，最终只用于证明“有记录”。
4. 不同 feature 任意选择是否拆 modules，结构失去一致性。
5. 测试和发布决策没有独立负责人，事故后无法判断哪一层遗漏。
6. 为解决膨胀，又重新发明 PRD、test plan、deploy plan，但命名和结构已不统一。

### 因果链

```text
追求更少文件
→ 合并不同消费者与更新周期
→ 单文件 interface 膨胀
→ 局部读取、所有权和独立验证变差
→ Agent 漏约束与同源错误增加
→ 再次拆文件且缺乏统一规则
```

### 被否方案及理由

| 方案 | 理由 |
|------|------|
| 所有阶段都固定生成独立文件 | 低风险小功能成本过高，重复严重 |
| 永远只有 project/goal/CU 三类文件 | 无法适应独立消费者、更新周期和高风险治理 |
| 完全由 Agent 自由决定是否拆分 | 输出形状不可预测，难验证、难训练使用习惯 |

## 结论

**判断**：三事实源适合作为默认最小核，不适合作为文档体系上限。

**置信度**：高

**依据**：

1. 文档独立性的根因是消费者、更新周期和验证责任，不是生命周期阶段。
2. 单大文件会降低 token locality 和 diff 语义。
3. 横切、高风险和独立审批信息不能可靠压入 goal/modules/CU。

**前提依赖**：如果 Forge 只服务单人、低风险、单 session 项目，则三事实源可以成为完整模型；否则必须允许受规则控制的独立文档。
